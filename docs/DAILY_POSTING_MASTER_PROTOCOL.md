# Daily Posting Master Protocol

Updated: 2026-08-30

이 문서는 So-dak의 신규 글 작성, 기존 글 개정, 예약 게시, 자동 게시 판단에 적용하는
최우선 기본 정책이다. 다른 게시 문서나 일정이 이 문서와 충돌하면 이 문서를 따른다.

## 1. 적용 우선순위

1. 이 문서의 게시·근거·품질·문체 기준
2. 대상 프로젝트의 현재 코드, 테스트, 설정, 로그, 공식 문서
3. `docs/WRITING_STYLE_GUIDE.md`의 세부 표현 기준
4. `docs/CONTENT_QUALITY_PLAN.md`의 개선 순서

이 문서는 So-dak 콘텐츠의 최상위 원칙이자 게시 판단의 단일 기준이다.
`docs/WRITING_STYLE_GUIDE.md`는 이 문서의 문체 원칙을 구체화하는 하위 가이드이며,
이 문서의 근거·보안·분량·게시 보류 조건을 완화하거나 대체할 수 없다.

`VoiceLink` 프로젝트는 해당 주제와 직접 관련된 경우 근거 자료로 참조할 수 있다.
다만 현재 체크아웃의 코드·문서·테스트에서 직접 확인되는 구현만 사용하고, 트래픽,
지연시간, 장애 효과, 사용자 수, 사업 성과처럼 확인되지 않은 수치나 결과는 만들지 않는다.

## 2. 게시 여부 결정

- 평일 07:00 KST는 목표 시간일 뿐, 품질 기준을 낮추는 게시 허가가 아니다.
- 검증된 코드, 설정, 로그, 측정값 또는 1차 출처가 없으면 새 글을 게시하지 않는다.
- 신규 기술 글과 대폭 개정한 기술 글은 공백을 제외한 순수 본문이 최소 4,000자여야 한다.
- 일반 기술 글은 5,000~7,000자를 권장한다. 복잡한 장애 분석이나 설계 글은 근거가
  충분할 때 7,000자 이상 작성할 수 있다.
- 분량을 셀 때 HTML, 목차, 코드 블록, Mermaid, 표 안의 코드, 이미지 설명, 관련 글 카드와
  참고 링크 목록은 제외한다. 독자가 읽는 설명 본문만 센다.
- 4,000자를 채우지 못한 글은 독립 검색 문서로 게시하지 않는다. 검증된 재현·실패 사례와
  운영 조건을 보강하거나, 같은 검색 의도의 기존 글에 통합한다.
- 새 근거가 부족하면 기존 글을 보강하거나 그날 게시를 건너뛴다.
- 실제로 사용하지 않은 Kafka, MSA 등의 기술을 경험담처럼 작성하지 않는다.
- 여러 글이 같은 검색 의도를 다루면 새 글을 늘리지 말고 가장 강한 글로 통합한다.
- 글자 수를 맞추기 위한 반복 문장, 정의 나열, 같은 결론의 재서술은 금지한다.

## 3. 근거 수집

- 글을 쓰기 전에 대상 저장소와 실행 환경을 직접 확인한다.
- VoiceLink를 참조할 때는 관련 모듈, 테스트, 설정과 운영 문서를 함께 확인한다.
- 동작이 버전에 따라 달라지면 소프트웨어와 의존성 버전을 기록한다.
- 공식 문서, 표준, 원본 저장소와 직접 관찰한 코드·로그를 우선한다.
- 검증 결과, 추론, 권장 사항, 실행하지 않은 예제를 문장에서 명확히 구분한다.
- 토큰, 비밀번호, 내부 주소, 운영 자격 증명, 개인정보와 원본 사용자 데이터는 공개하지 않는다.

## 4. 필수 글 구조

1. 독자가 해결하려는 문제, 실행 환경, 전제조건과 주장의 범위를 먼저 밝힌다.
2. 원인은 확보한 근거가 설명할 수 있는 깊이까지만 다룬다.
3. 재현 방법, 구현, 실패 처리, 타임아웃·재시도와 롤백 조건을 보여준다.
4. 결과는 환경과 표본을 포함해 측정한다. 측정하지 않았다면 목표나 예상으로 표시한다.
5. 한계와 적용하지 말아야 할 조건을 적는다.
6. 관련 글은 본문 맥락에서 연결하고 마지막에 1차 출처를 정리한다.

각 핵심 절은 제목만 두지 말고 맥락, 근거, 판단을 포함한 2개 이상의 실질적인 문단으로
설명한다. 코드만 길게 붙여 본문 분량을 대신하지 않는다.

## 5. 코드와 운영 품질

- 예제에는 필요한 오류 처리, 소유권, 트랜잭션 경계, 멱등성, 타임아웃과 재시도를 포함한다.
- 축약하거나 설명용으로 만든 코드는 개념 예제라고 표시하고 운영 준비 상태로 오해시키지 않는다.
- 코드와 본문에서 사용하는 이름, 상태, API, 설정값이 서로 일치해야 한다.
- Mermaid는 시퀀스, 상태 전이, 소유 관계나 다중 컴포넌트 흐름을 더 명확히 할 때만 사용한다.
- Mermaid와 코드 블록은 데스크톱과 모바일에서 실제 렌더링을 확인한다.

## 6. SEO와 콘텐츠 품질

- 설명적인 H1 하나, 고유한 제목과 메타 설명, canonical URL, 관련 소셜 이미지를 사용한다.
- **대표 커버 이미지 맞춤 생성 (Custom Featured Image)**:
  - 기계적인 기본 템플릿 이미지를 지양하고, 해당 글의 핵심 기술 주제(Redis Lua Script, PostgreSQL COPY, Airflow DAG, WebRTC LiveKit 등)를 시각화한 고품질 3D 에디토리얼 테크 이미지를 맞춤 생성하여 등록한다.
  - 16:9 비율, 다크 슬레이트 배경, 왜곡 없는 직관적 기술 컴포넌트 일러스트를 표준으로 한다.
- **마크다운 원문 버전 관리 아카이빙 (.md Source Archiving)**:
  - 워드프레스에 발행된 모든 기술 아티클은 원본 마크다운 파일(`.md`)을 `wp-local/posts/{YYYY-MM-DD-slug}.md` 및 `career-ops/docs/posts/`에 영구 보관하고 깃(Git)으로 버전 관리한다.
- 내부 링크는 `https://so-dak.com/...` 공개 canonical 주소만 사용한다.
- `localhost`, 원시 글 ID와 스테이징 주소를 게시 본문에 넣지 않는다.
- 관련 개념을 설명하는 문단에서 자연스럽게 내부 링크를 연결한다.
- 반복 링크 카드, 키워드 치환형 글, 근거 없는 대량 생성 콘텐츠를 게시하지 않는다.
- 이미지와 다이어그램은 실제 흐름, 실패, 결과 또는 비교를 설명해야 한다.

## 7. 기본 문체와 말투

세부 표현 기준은 `docs/WRITING_STYLE_GUIDE.md`를 따르되, 최종 판단은 이 문서를 기준으로
한다. 자연스러운 말투를 만들기 위해 근거가 없는 경험이나 감정을 추가해서는 안 된다.

- 처음부터 답을 알고 있었던 것처럼 쓰지 않는다. 처음 생각, 막힌 지점, 확인한 근거,
  바꾼 판단을 실제 순서대로 적는다.
- 실제로 겪은 장애·실험·판단 전환만 1인칭으로 쓴다. 개념 글이나 도입 검토 글에는
  경험담을 만들지 말고 현재 코드에서 확인한 범위와 공식 문서 기준을 밝힌다.
- 개발자가 동료에게 설명하듯 솔직하게 쓴다. 회고 글은 `-했다`, 안내 글은 `-합니다`를
  쓸 수 있지만 한 문단 안에서 말투를 섞지 않는다.
- 도입은 당시의 질문이나 오해뿐 아니라 실패한 테스트, 실제 로그, 코드 차이, 실행 계획,
  측정값처럼 검증 가능한 출발점에서 짧게 시작할 수 있다. 여러 글에 같은 도입 공식을
  반복하지 않고 실행 환경과 주장의 범위를 초반에 밝힌다.
- 문단은 한두 문장을 기본으로 하되 길이를 기계적으로 맞추지 않는다.
- 소제목과 문단 수를 할당량처럼 맞추지 않는다. 서로 이어지는 절은 합치고, 비교가
  핵심이면 표나 하나의 판단 절로 묶어 보고서식 분절을 피한다.
- `현재 구현은`, `운영에서는`, `있다`, `한다`, `않는다`, `확인해야 한다` 같은 표현이
  연속되지 않게 문장 시작과 종결의 리듬을 바꾼다.
- 영어 기술 용어는 코드와 표준 이름을 정확히 가리킬 때 사용하되 한 문장에 여러 용어를
  쌓지 않는다. 처음 뜻을 밝힌 뒤에는 일관된 용어나 자연스러운 한국어 표현을 사용한다.
- `삽질`, `헷갈렸다` 같은 말은 실제 전환점에서만 드물게 쓴다.
- 코드 앞에는 필요했던 이유를, 코드 뒤에는 달라진 동작과 확인 결과를 쓴다.
- “이번 글에서는 살펴보겠습니다”, 반복되는 “결론적으로”, 근거 없는 과장과 교과서식
  정의 나열을 피한다.
- 마무리는 본문 전체를 다시 요약하지 않는다. 가장 크게 바뀐 판단, 아직 증명하지 못한
  한계, 다음에 먼저 확인할 항목 가운데 필요한 것만 짧게 남긴다.
- 참고 문체의 표현을 복사하지 않는다. 말투보다 이 문서의 근거·보안·품질 규칙이 우선이다.

## 8. 완료 조건

다음 항목을 모두 충족해야 게시할 수 있다.

- 핵심 주장마다 코드, 로그, 측정 또는 1차 출처가 있다.
- 예제와 설명이 내부적으로 일관되고 실패 경로가 빠지지 않았다.
- 공개 링크와 1차 출처가 정상 응답하며 주장과 직접 관련된다.
- 제목, 설명, H1, OG 이미지, canonical과 구조화 데이터가 유효하다.
- 비밀값과 개인정보가 포함되지 않았다.
- 데스크톱과 모바일 화면을 확인했고 깨진 코드·다이어그램·이미지가 없다.
- 확인하지 못한 결과를 실제 성과처럼 표현하지 않았다.
- 근거 없는 1인칭 경험을 만들지 않았고, 도입·소제목·문단·결말이 다른 글의 공식을
  기계적으로 반복하지 않는다.
- 같은 종결어미와 영어 기술 명사가 연속돼 글이 보고서나 번역문처럼 굳지 않았다.
- 마무리가 본문을 재요약하지 않고 바뀐 판단이나 다음 검증 항목으로 끝난다.
- 공백과 비본문 요소를 제외한 설명 본문이 4,000자 이상이다.

한 항목이라도 충족하지 못하면 예약 시간을 미루고 보강하거나 게시하지 않는다.
