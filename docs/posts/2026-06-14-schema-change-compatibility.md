엔티티에 필드를 추가하고 애플리케이션이 켜졌다는 사실만으로 스키마 변경이 끝난 것은 아니다. 이미 저장된 데이터가 어떤 값을 가질지, 아직 교체되지 않은 서버가 같은 테이블을 읽을 수 있을지까지 확인해야 배포 순서가 정해진다.

기존 글은 Flyway를 도입해 안전하게 변경한 경험처럼 쓰여 있었지만 현재 VoiceLink 빌드에는 그 도구가 포함되어 있지 않았다. 실제 설정은 Hibernate의 ddl-auto를 validate로 두고 스키마를 사전에 반영하는 방식이다. 도구 이름보다 지금 변경을 어떻게 수행하는지부터 맞춰 적었다.

검토한 근거는 Spring Boot 3.2.5의 설정과 빌드 파일, Outbox 임대 처리용 PostgreSQL SQL, 회사 이메일·사용자 안전 기능의 스키마 문서다. 실제 운영 데이터베이스에 이 글의 명령을 실행한 것은 아니다. 아래 절차는 확인한 변경 구조와 배포 전에 검증할 조건을 설명한다.

## 검증 설정이 해 주지 않는 일

validate는 애플리케이션이 기대하는 매핑과 데이터베이스 구조가 맞는지 기동 시 검사하는 역할을 한다. 누락된 테이블과 컬럼을 알아서 만들거나 기존 행을 새 업무 규칙에 맞게 변환하는 배치가 아니다. 빈 데이터베이스에 앱을 띄우면 자동으로 서비스가 준비된다고 기대해서는 안 된다.

반대로 검증을 통과했다고 모든 인덱스와 제약, 데이터의 의미가 올바르다는 보장도 아니다. ORM이 확인하는 구조와 서비스가 요구하는 규칙의 범위가 다르기 때문이다. 고유 제약이나 부분 인덱스, 기존 데이터의 상태 분포는 별도로 조회해 확인할 대상이다.

테스트 설정은 운영과 다르게 create-drop을 사용한다. 테스트가 새 스키마를 만들고 제거하는 환경에서 통과했다는 사실은, 과거 데이터가 들어 있는 운영 스키마를 안전하게 바꿨다는 증거가 아니다. 새 구조의 기능 테스트와 기존 구조에서 넘어오는 전환 테스트를 구분해야 한다.

자동 update 설정을 끄는 이유를 모든 자동 변경은 위험하다는 문장으로 끝내고 싶지는 않았다. 핵심은 변경 의도와 실행 순서, 적용 이력을 리뷰 가능한 형태로 남기는 일이다. 도구를 쓰든 수동 SQL을 쓰든 기존 데이터와 구버전의 요구를 확인하지 않으면 같은 문제가 남는다.

수동 방식을 유지한다면 누가 어느 환경에 어떤 파일을 적용했는지 기록해야 한다. 저장소에 SQL이 있다는 사실만으로 운영 적용이 증명되지 않는다. 실행 시각과 대상 버전, 확인 쿼리 결과를 남겨야 다음 배포에서 다시 추측하지 않을 수 있다.

## 상태 컬럼을 추가하는 것보다 해석이 어려웠다

[Outbox 변경 SQL](https://so-dak.com/%eb%b6%84%ec%82%b0-%ec%8b%9c%ec%8a%a4%ed%85%9c-%ec%a0%95%ed%95%a9%ec%84%b1-%eb%b3%b4%ec%9e%a5-transactional-outbox-pattern%ec%9c%bc%eb%a1%9c-%eb%a7%a4%ec%b9%ad-%ec%9d%b4%eb%b2%a4%ed%8a%b8-%eb%b0%9c/)은 상태, 다음 시도 시각, 임대 만료 시각, 임대 식별자 컬럼을 먼저 추가한다. 새 컬럼이 존재해야 새 코드가 작업을 선점하고 완료를 기록할 수 있다. 하지만 컬럼 추가만으로 기존 행의 업무 상태가 정해지지는 않는다.

기존 데이터에는 보낸 시각이 있는데 오류도 남아 있는 행이 있을 수 있다고 SQL 주석이 설명한다. 과거 구현이 최대 재시도 실패에도 보낸 시각을 채웠기 때문이다. 이 경우 시각이 있다는 이유만으로 모두 발송 성공으로 옮기면 실패 작업을 성공으로 바꾸게 된다.

변환 SQL은 보낸 시각과 오류 유무를 함께 사용해 상태를 정하고, 실패로 옮긴 행의 보낸 시각을 비운다. 이 부분은 자료형 변환보다 업무 의미의 변환이다. 어떤 조합이 실제로 얼마나 존재하는지 확인하고 예외 사례가 없는지 검토해야 안전한 기준이 된다.

다음 시도 시각도 기존 생성 시각 등을 기준으로 채운다. 이미 오래된 작업을 새 규칙에 넣었을 때 즉시 한꺼번에 선점되는지 살펴야 한다. 데이터 변환은 성공했는데 배포 직후 외부 전송이 몰리는 상황이 생길 수 있기 때문이다.

그래서 적용 전에는 전체 행 수만 보는 대신 상태 전환에 쓰이는 값의 조합별 건수를 확인하는 편이 좋겠다. 변경 후에는 예상한 상태의 건수와 미분류 행을 비교한다. 개인정보나 메시지 본문을 꺼내지 않고도 변환 규칙의 적용 범위를 점검할 수 있다.

이 글에서 특정 행 수나 발송 실패 복구 성과를 쓰지 않은 이유도 같다. SQL의 의도를 확인한 것과 실제 운영 자료의 분포를 확인한 것은 다른 단계다. 코드에 적힌 변환식을 읽고 장애가 해결되었다고 결론 내릴 수는 없다.

## 추가하고 채운 뒤 제약을 건다

일반적인 전환에서는 새 컬럼을 먼저 허용 가능한 형태로 추가하고, 기존 데이터를 채운 다음, 새 제약을 적용하는 순서를 검토한다. 이미 값이 없는 행이 많은데 바로 NOT NULL을 강제하면 변경이 실패하거나 오래 검증할 수 있다. 각 단계에서 무엇이 허용되는지 정해야 한다.

확인한 SQL도 상태를 채운 뒤 기본값과 NOT NULL을 설정한다. 기본값은 이후 삽입에서 값을 생략했을 때 적용되는 정책이며, 기존 모든 업무 상태를 올바르게 추론해 주는 기능은 아니다. 과거 행의 변환과 새 쓰기의 기본 동작을 나눠 둔 것이다.

아래는 흐름만 보여 주는 설명용 예제다. 실제 테이블과 상태 의미는 각 업무에 맞춰 정해야 하며, 데이터 규모에 따른 잠금과 실행 시간은 이 예제에서 검증하지 않았다.

```sql
ALTER TABLE work_items ADD COLUMN status varchar(20);
-- 기존 행의 업무 의미를 검토한 별도 변환 수행
-- 새 코드가 쓰는 값과 미변환 행을 확인
ALTER TABLE work_items ALTER COLUMN status SET DEFAULT 'PENDING';
ALTER TABLE work_items ALTER COLUMN status SET NOT NULL;
```

여러 단계로 나누는 동안 구버전 애플리케이션이 계속 쓰고 있다면 변환 중 새로 생긴 행도 고려해야 한다. 한 번 UPDATE를 끝냈다고 그 뒤의 모든 쓰기가 새 형식을 따르지는 않는다. 기본값과 호환 쓰기, 추가 변환 중 어느 방법으로 빈틈을 닫을지 정할 필요가 있다.

컬럼 이름을 바로 바꾸거나 삭제하는 변경은 더 신중해야 한다. 구버전 서버가 살아 있는 동안 이전 이름을 사용하면 요청이 실패한다. 새 컬럼을 추가해 양쪽 버전이 공존할 시간을 둔 뒤 읽기·쓰기를 옮기고 마지막에 정리하는 방식이 한 가지 대안이다.

공존 기간에 두 컬럼을 함께 쓴다면 어느 값이 기준인지도 필요하다. 한쪽만 갱신되었을 때의 복구와 데이터 검증이 없으면 단순한 중복 저장이 된다. 변경을 여러 배포로 나누는 대신, 각 중간 상태를 서비스가 읽을 수 있도록 정의해야 한다.

## 인덱스를 만드는 동안에도 요청은 들어온다

Outbox 선점에는 실행 예정 시각과 식별자 순서, 미완료 상태를 조건으로 사용하는 부분 인덱스가 추가된다. 쿼리가 찾는 행을 좁히려는 목적이 SQL에 드러난다. 인덱스가 있다는 사실만으로 모든 데이터 분포에서 빠른 계획을 선택한다고 볼 수는 없다.

파일은 CREATE INDEX CONCURRENTLY를 사용하고 전체를 하나의 BEGIN으로 감싸지 말라고 명시한다. 이 명령은 일반 인덱스 생성과 실행 제약이 다르다. 모든 변경을 무조건 한 트랜잭션으로 묶는 규칙을 적용하면 실행 자체가 실패할 수 있다.

동시 생성은 일반 쓰기 작업에 미치는 잠금 영향을 줄이는 데 쓰이지만 비용이 없는 작업은 아니다. 테이블을 읽고 자원을 사용하며 다른 트랜잭션을 기다릴 수 있다. 데이터가 큰 환경에서는 작업 시간과 여유 공간, 읽기 부하를 검토해야 한다.

실패 후에는 같은 이름의 인덱스가 남았는지만 볼 것이 아니라 유효한 상태인지 확인해야 한다. IF NOT EXISTS는 이름이 존재할 때 생성을 건너뛰는 조건이지, 그 인덱스가 기대한 정의와 상태라는 검증은 아니다. 재실행 가능성과 결과 검증은 별개다.

같은 주의는 ADD COLUMN IF NOT EXISTS에도 적용된다. 이름이 같은 컬럼의 타입이나 기본값이 잘못되어 있어도 파일이 그 차이를 자동 수정해 주지는 않는다. 변경 전후 실제 정의를 비교하고 저장소의 SQL과 다른 부분을 명시적으로 처리해야 한다.

확인 쿼리는 결과 이름만 나열하는 것에서 한 단계 더 나아갈 수 있다. 인덱스 정의와 유효 상태, 대상 쿼리의 실행 계획을 함께 남기면 나중에 같은 변경을 평가하기 쉽다. 실제 실행을 수반하는 계획 분석은 서비스 영향이 적은 환경과 범위부터 시작해야 한다.

## 실패했을 때 앱만 되돌릴 수 있을까

애플리케이션 이미지를 이전 버전으로 바꾸는 것과 데이터베이스를 이전 상태로 되돌리는 것은 다르다. 새 컬럼을 추가한 변경은 구버전이 무시할 수 있지만, 컬럼을 삭제하거나 상태의 의미를 바꾼 변경은 코드만 되돌려도 복구되지 않을 수 있다.

배포 전에 되돌릴 버전이 새 스키마를 읽고 쓸 수 있는지 확인해야 한다. 구버전으로 실제 요청을 수행해 보는 검증이 단순 기동 성공보다 낫다. 새 상태 값이 enum 변환에서 실패하거나 이전 쿼리가 다른 행을 고를 수 있기 때문이다.

데이터 변환을 역으로 수행할 수 있는지도 따로 본다. 여러 옛 상태를 하나로 합쳤다면 역변환만으로 원래 값을 복원할 수 없다. 원본 정보를 보존하거나 재생성할 수 있는 근거가 있어야 하고, 그렇지 않다면 되돌리기보다 앞으로 고치는 복구를 선택해야 할 수 있다.

백업이 있다는 말도 복원 시간과 손실 가능한 변경량을 설명하지 못하면 충분하지 않다. 백업 이후 들어온 정상 쓰기를 어떻게 다룰지, 복원 중 서비스를 어떻게 제한할지까지 계획에 포함되어야 한다. 백업 파일 존재와 복원 검증 완료는 서로 다른 상태다.

명령 제한 시간도 계획에 넣는다. 잠금 획득이 오래 걸리면 무작정 대기하면서 뒤의 요청까지 영향을 줄 수 있다. 허용한 시간 안에 시작하지 못하면 중단하고 다시 검토할 수 있도록 잠금 대기와 전체 실행 제한을 구분해 설정하는 방안을 검토한다.

변경 중 오류가 났을 때는 어느 문장까지 커밋되었는지를 먼저 확인해야 한다. 파일 전체가 한 트랜잭션이 아니라면 앞부분은 반영되고 뒷부분만 실패할 수 있다. 같은 파일을 다시 실행하기 전에 각 단계의 사전 조건과 완료 조건을 다시 읽어야 하는 이유다.

## 마이그레이션 도구를 쓴다면 달라지는 것

버전 관리 도구를 도입하면 변경 파일의 적용 순서와 이력을 일정한 방식으로 관리할 수 있다. 수동 실행에서 빠뜨리기 쉬운 중복 적용이나 파일 변경을 발견하는 데 도움이 될 수 있다. 하지만 파일 안의 데이터 변환이 업무적으로 옳은지는 여전히 작성자와 검증의 책임이다.

이미 운영 중인 데이터베이스에 도구를 붙일 때는 기존 상태를 시작점으로 어떻게 등록할지도 정해야 한다. 빈 데이터베이스용 초기화 파일을 운영에 그대로 실행하면 충돌할 수 있다. 현재 정의를 기준으로 삼는 절차와 이후 변경의 범위를 검토해야 한다.

여러 인스턴스가 동시에 시작할 때 누가 변경을 수행할지, 앱 기동과 분리된 작업으로 실행할지 역시 선택이다. 도구가 잠금을 제공하더라도 긴 변환을 앱 시작 시간에 포함하면 배포 대기와 장애 판단이 달라진다. 변경과 서비스 시작의 책임을 분리하면 상황을 읽기 쉬워진다.

이번 글에서는 아직 사용하지 않는 Flyway를 도입 경험으로 남기지 않았다. 도입한다면 먼저 기존 수동 SQL을 기준으로 테스트 데이터베이스를 만들고, 새 버전으로 전환한 뒤 구버전 호환까지 확인할 계획을 세워야 한다. 도구 교체 자체를 안전성의 결과로 쓰지는 않으려 한다.

## 배포 확인은 데이터가 있는 상태에서

검증용 데이터에는 정상 행만 넣지 않는다. 과거 오류가 기록된 행, 값이 비어 있는 행, 같은 시각을 가진 작업처럼 실제 변환 분기를 지나갈 사례가 필요하다. 변환 전의 의미와 변환 후 기대 상태를 짝지어 두면 쿼리 성공만 확인하는 것보다 정확하다.

새 스키마에서 새 코드의 기능 테스트를 돌리고, 공존시킬 구버전의 읽기와 쓰기도 시험한다. 이어서 일부 단계가 실패한 상태에서 재실행하는지 확인한다. 멱등적으로 보이는 SQL도 부분 적용 상태에서 같은 최종 구조에 도달하는지를 직접 검증해야 한다.

운영 적용 후에는 기동 로그와 실제 구조, 대표 요청을 함께 본다. 오류가 없다는 로그만으로 오래된 작업이 잘못된 상태로 변환되지 않았다고 알 수는 없다. 반영한 변경의 목적에 맞는 상태 분포와 실행 계획을 확인해야 완료라고 적을 수 있다.

앞으로 스키마 변경을 설명할 때 먼저 남길 것은 도구 이름이 아니라 중간 상태다. 어느 단계에서 구버전과 새 버전이 무엇을 읽고 쓰는지 표로 적을 수 있다면, 배포와 복구 순서도 훨씬 구체적으로 정할 수 있다.
