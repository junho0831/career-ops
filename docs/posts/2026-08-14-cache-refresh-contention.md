캐시가 있으면 같은 조회를 덜 하게 된다. 그런데 여러 요청이 동시에 캐시가 없다는 사실을 확인하면, 그 요청들은 모두 원본을 조회하러 갈 수 있다. 만료 시간을 정하는 일과 만료 직후 몰리는 요청을 처리하는 일은 따로 봐야 했다.

이번에는 VoiceLink의 방 상태 조회 코드를 출발점으로 삼았다. 같은 [통화 세션](https://so-dak.com/webrtc-livekit-%ec%97%b0%eb%8f%99-%ed%9a%8c%ea%b3%a0-%ea%b7%b8%eb%83%a5-%ec%98%a4%ed%94%88%ec%86%8c%ec%8a%a4-%ec%84%9c%eb%b2%84-%eb%9d%84%ec%9a%b0%eb%a9%b4-%eb%90%98%eb%8a%94-%ea%b1%b0-%ec%95%84/)의 재접속 요청이 겹쳤을 때 LiveKit 상태를 중복 조회하지 않도록 짧은 캐시와 로컬 잠금이 들어 있다. Java 17과 Spring Boot 3.2.5의 현재 코드에서 확인한 사례다. Redis 분산 락과 Redisson 부분은 그 구조를 여러 서버로 넓힐 때의 검토이며, 실제 도입 성과로 쓰지 않았다.

## 만료 시각보다 조회가 겹치는 구간

캐시를 읽고 값이 없으면 원본을 조회한 뒤 저장하는 흐름은 단일 요청에서는 자연스럽다. 두 요청을 나란히 놓으면 다른 모습이 보인다. 첫 요청이 원본 응답을 기다리는 동안 두 번째 요청도 캐시가 비었다고 판단한다. 만료 시간이 길어도 이 틈 자체가 사라지지는 않는다.

원본 조회가 느려지면 그 틈에 들어오는 요청 수가 늘어난다. 원본에 추가 부하가 걸리고 응답이 더 느려지는 방향으로 번질 수도 있다. 여기서 필요한 것은 캐시의 존재 여부뿐 아니라 누가 지금 갱신하고 있는지를 판단하는 방법이다. 같은 값을 만드는 요청을 합칠지, 잠시 기다릴지, 다른 응답을 줄지부터 정해야 한다.

모든 키를 하나의 잠금으로 묶으면 다른 데이터 조회까지 기다린다. 같은 세션의 방 상태를 중복 조회하지 않으려던 장치가 서로 관계없는 통화의 재접속까지 막을 수 있는 셈이다. 잠금 범위를 캐시 키와 맞추는 이유가 여기에 있다. 다만 키마다 무제한으로 잠금 객체를 만들면 그 객체를 정리하는 문제도 생긴다.

현재 방 상태 캐시는 정해진 개수의 잠금 객체 중 세션 식별자의 해시로 하나를 고른다. 메모리 사용을 제한하는 대신 다른 세션이 같은 잠금을 공유할 수 있다. 같은 키만 완전히 독립된 잠금을 갖는다고 설명하면 부정확하다. 설계가 얻는 단순함과 충돌 가능성을 함께 적어야 실제 코드와 맞는다.

## 잠금을 얻은 뒤 다시 읽는 이유

첫 번째 캐시 확인은 잠금을 잡지 않고 빠르게 끝내기 위한 경로다. 값이 없거나 오래됐을 때만 잠금 구간으로 들어간다. 여기서 바로 원본을 조회하면 먼저 들어갔던 요청이 갱신을 끝냈어도 뒤따른 요청이 똑같은 일을 한다. 잠금 획득 뒤 한 번 더 읽는 조건이 있어야 기다린 의미가 생긴다.

아래는 현재 구현의 중요한 순서만 남긴 개념 예제다. 캐시 만료 검사와 저장소 호출의 실제 타입은 생략했다. 모든 요청을 잠금에 넣는 코드가 아니라, 값이 유효할 때는 바로 반환하고 갱신이 필요할 때만 요청을 합치는 구조를 보여 준다.

```java
var cached = cache.get(key);
if (isFresh(cached)) {
    return cached.value();
}
synchronized (lockFor(key)) {
    var refreshed = cache.get(key);
    if (isFresh(refreshed)) {
        return refreshed.value();
    }
    var value = loadFromOrigin(key);
    cache.put(key, snapshot(value));
    return value;
}
```

두 번째 요청이 잠금을 얻었을 때 첫 요청이 만든 스냅샷이 아직 유효하면 원본 호출을 생략할 수 있다. 현재 테스트에는 같은 세션으로 여덟 요청이 동시에 진입하는 상황을 만들고, 가짜 방 상태 조회가 한 번 호출되는지 확인하는 경우가 있다. 실제 외부 API의 처리량을 측정한 결과가 아니라 요청을 합치는 분기를 검증하는 테스트다.

짧은 캐시도 오래된 값을 읽는 시간은 만든다. 참가자가 방을 나간 직후에 이전 스냅샷을 재사용할 수 있으므로 캐시 수명과 허용 가능한 상태 지연을 연결해야 한다. ‘짧으니 안전하다’고 끝내기보다, 이 조회 결과가 통화 유지나 종료 판단에 어떻게 쓰이는지 따져야 한다. 조회 비용만 보고 정할 값이 아니었다.

현재 캐시는 프로세스 메모리에 있으므로 서버가 두 대면 각자 갱신할 수 있다. 같은 프로세스 안의 동시 조회를 줄인 사실과 전체 서버에서 한 번만 조회한다는 보장은 다르다. 이 정도 중복을 허용할 수 있다면 로컬 잠금만으로도 충분할 수 있다. 굳이 외부 락을 더하기 전에 원본이 감당해야 할 중복의 상한을 보는 편이 낫다.

## Redis 락은 갱신 소유자를 표시한다

여러 서버의 갱신을 합쳐야 한다면 공유 저장소에 소유권을 기록할 수 있다. 단일 Redis를 사용하는 기본 형태는 키가 없을 때만 임의 토큰과 만료 시간을 함께 설정하는 것이다. 값이 있는지 확인한 뒤 별도로 쓰는 두 명령으로 나누면 그 사이의 경합이 다시 생긴다.

토큰은 누가 잠금을 얻었는지를 구분하기 위한 값이다. 고정된 문자열만 넣으면 나중에 잠금을 해제하는 요청이 지금 남아 있는 잠금의 주인인지 알기 어렵다. 갱신이 길어져 잠금이 만료된 뒤 다른 요청이 새 잠금을 얻는 경우까지 생각하면, 해제할 때도 소유권을 확인해야 한다는 이유가 보인다.

예를 들어 A의 잠금이 만료되어 B가 새로 얻었는데 A가 뒤늦게 단순 삭제를 실행하면 B의 잠금까지 없어질 수 있다. 저장된 토큰이 내 토큰과 같은 경우에만 원자적으로 지우는 연산이 필요하다. 단순 비교 후 삭제를 별도 요청으로 보내면 그 사이에 주인이 바뀔 수 있으므로 이 두 단계도 묶어야 한다.

그렇다고 토큰 비교만으로 오래된 갱신 결과의 쓰기까지 막히지는 않는다. 늦게 돌아온 A가 B보다 오래된 값을 캐시에 덮어쓸 수 있다. 갱신 대상의 버전이나 세대 번호를 함께 검사할지, 늦은 결과를 버릴지, 원본에서 순서를 보장할지를 별도로 정해야 한다. 락을 잘 해제하는 것과 올바른 값을 쓰는 것은 다른 조건이다.

Redis가 재시작하거나 장애 조치되는 경우도 분리해서 생각해야 한다. 복제와 장애 조치 설정에 따라 잠금 상태가 보존되는 방식이 달라질 수 있다. 캐시를 중복 갱신하는 정도를 허용할 수 있는 설계와 금전·재고처럼 중복 효과를 허용하기 어려운 설계는 같은 락 예제를 그대로 공유할 수 없다. 이 글은 후자의 정합성 보장을 주장하지 않는다.

## 기다리는 요청에 무한 대기는 없다

잠금을 못 얻은 요청을 모두 원본으로 보내면 갱신 경합을 막으려던 목적이 사라진다. 반대로 아무 제한 없이 기다리게 두면 응답 시간과 연결 수가 늘어난다. 기다릴 최대 시간, 재확인 간격, 기다린 뒤에도 값이 없을 때의 응답을 먼저 정해야 한다. 락 획득 코드보다 이 정책이 사용자에게 더 직접적으로 드러난다.

짧게 재확인하더라도 모든 요청이 같은 간격으로 깨어나면 Redis에 작은 파동이 반복될 수 있다. 재시도 간격에 분산을 주는 방법을 검토할 수 있지만, 횟수와 총 시간에 상한이 있어야 한다. 상한이 끝났을 때는 명시적으로 실패를 반환하거나 허용된 대체 응답을 선택해야 한다. 아무 응답이나 성공으로 바꾸면 장애를 숨기게 된다.

오래된 값을 잠시 제공할 수 있는 데이터라면 갱신 중 기존 값을 재사용하는 방식도 가능하다. 그러나 삭제된 권한이나 이미 종료된 세션처럼 오래된 값이 잘못된 결정을 만드는 경우에는 맞지 않을 수 있다. 신선도 허용 범위를 정하지 않은 채 오래된 캐시를 만능 해결책으로 넣으면 응답 속도와 데이터 의미를 맞바꾸게 된다.

원본이 비어 있다는 결과를 캐시할 때도 구분이 필요하다. 정상적으로 대상이 없다는 것과 조회에 실패해 결과를 얻지 못했다는 것은 다르다. 오류를 빈 결과로 저장하면 원본이 복구된 뒤에도 한동안 없다는 응답을 반복할 수 있다. 현재 코드가 어떤 예외를 어떤 값으로 바꾸는지 호출 계층까지 따라가야 하는 이유다.

원본 호출에는 별도의 제한 시간도 필요하다. 락의 만료 시간만 정하면 갱신 작업 자체가 그 시간에 중단될 것 같지만 그렇지 않다. 네트워크 요청은 계속 진행 중일 수 있고, 늦은 응답이 돌아와 캐시를 수정할 수도 있다. 호출 취소가 실제로 적용되는지와 취소 뒤 결과를 처리하지 않는 조건까지 보아야 한다.

## Redisson을 고를 때도 트랜잭션은 남는다

Redisson은 락 대기, 소유권, 임대 시간과 갱신 같은 기능을 제공한다. 그렇다고 라이브러리 이름이 있으면 모든 동시성 문제가 끝나는 것은 아니다. 명시적 임대 시간을 쓰는 호출과 watchdog이 갱신하는 호출은 조건이 다르므로 사용한 API와 설정을 함께 읽어야 한다. 현재 VoiceLink 의존성에는 Redisson이 없어 이 부분은 도입 검토로 남겼다.

기존 글에서는 Lettuce를 스핀 락 방식 자체처럼 설명했는데, 클라이언트 라이브러리와 그 위에 만든 재시도 알고리즘을 혼동한 표현이었다. 단순 반복 조회를 선택한 코드가 부하를 만들 수 있는 것이지 클라이언트 이름만으로 모든 사용 방식이 정해지는 것은 아니다. 비교 대상은 같은 작업을 어떤 대기 정책으로 처리하는 코드여야 한다.

데이터베이스 갱신까지 보호하려면 락 해제가 커밋보다 앞서는지 살펴야 한다. 메서드 본문이 끝나기 전에 finally에서 락을 풀고, 트랜잭션 프록시가 그 뒤에 커밋한다면 다음 요청은 이전 변경이 확정되기 전에 들어올 수 있다. 어노테이션의 배치나 정수 우선순위만 외우기보다 실제 호출 순서를 그려 보는 편이 이해하기 쉽다.

명확한 경계를 만들려면 바깥에서 락을 얻고, 별도 트랜잭션 호출이 끝난 뒤 바깥에서 해제하는 구조를 검토할 수 있다. 그래도 커밋 실패, 인터럽트, 임대 시간 초과와 해제 실패를 어떻게 전달할지는 남는다. 해제 예외를 조용히 삼켜 버리면 소유권이 언제 사라졌는지 추적하기 어려우므로 예상한 경우와 조사할 오류를 구분해야 한다.

데이터베이스의 제약 조건과 멱등성은 이 설계에서도 필요하다. 분산 락을 넣었다는 이유로 고유 키나 조건부 갱신을 제거하면 락을 거치지 않는 코드 경로와 장애 상황에서 보호가 사라진다. 모든 쓰기 경로가 같은 규칙을 지키는지도 검토해야 한다. 락은 데이터 의미를 대신 설명해 주는 장치가 아니다.

## 성공률보다 실패 구간부터 시험한다

정상적인 단일 요청은 경합을 거의 드러내지 않는다. 같은 키를 동시에 요청하고 캐시가 처음부터 있는 경우, 없는 경우, 갱신 중 만료되는 경우를 나눠야 한다. 원본 조회 횟수, 대기 시간과 반환값을 같이 봐야 요청을 합친 대신 잘못된 값을 준 것은 아닌지 확인할 수 있다.

느린 갱신자를 만들고 잠금 만료 뒤 두 번째 갱신자를 진입시키는 실험은 소유권 문제를 드러내기 좋다. 먼저 시작한 요청을 나중에 끝내고, 새 잠금을 삭제하거나 새 값을 덮어쓰지 않는지 확인한다. 순서를 의도적으로 통제해야 잠깐 운 좋게 통과한 실행을 안전성의 근거로 삼지 않을 수 있다.

원본 조회 실패와 Redis 장애를 동시에 정상적인 캐시 미스로 세지 않는 것도 중요하다. 지표가 모두 미스로 합쳐지면 캐시 정책이 나쁜 것인지 외부 서비스가 멈춘 것인지 구분하기 어렵다. 조회 실패, 락 대기 만료, 소유권 상실과 정상 갱신을 따로 기록하되 키와 응답에 민감한 정보가 들어가지 않도록 해야 한다.

키 종류가 많은 환경에서는 하나의 인기 키와 여러 종류의 키를 따로 시험한다. 같은 키의 요청을 잘 합쳐도 서로 다른 키의 갱신이 한꺼번에 몰리면 원본 부하는 남는다. 만료 시간에 분산을 주거나 전체 갱신 동시성을 제한하는 방식은 이 경우의 별도 선택지다. 하나의 잠금 테스트를 전체 용량 시험으로 확대 해석하지 않는 편이 맞다.

로컬 캐시라면 만료된 항목이 언제 메모리에서 제거되는지도 확인해야 한다. 유효기간 검사로 사용하지 않는 것과 맵에서 항목을 지우는 것은 다르다. 현재 방 상태 코드는 일부 세션 종료 경로에서 캐시를 제거하지만, 장기간 다양한 키가 들어오는 경우의 정리 정책까지 자동으로 보장한다고 쓰지는 않았다.

캐시를 살펴볼 때 먼저 묻게 된 것은 TTL을 몇 초로 둘지가 아니다. 같은 값을 만드는 요청이 겹치면 누가 일을 맡고, 나머지는 얼마나 기다리며, 주인이 사라지면 어떤 응답을 받을지다. 이 세 가지를 설명하지 못한 상태에서는 락 라이브러리를 바꿔도 글의 빈 부분이 그대로 남는다. 다음 실험은 늦은 갱신 결과가 새 값을 덮어쓰는 경계부터 시작하려고 한다.
