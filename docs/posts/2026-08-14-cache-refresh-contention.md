`ActiveSessionResolver`에는 같은 캐시를 두 번 읽는 코드가 있다. 한 번은 잠금 밖에서, 한 번은 안에서 읽는다.

방금 봤잖아. 굳이 또?

VoiceLink의 동시성 점검 문서에는 이 코드가 필요한 이유가 남아 있다. 재접속 요청마다 LiveKit 방 상태를 물으면 같은 방으로 몰린 요청 수만큼 외부 호출도 늘어난다는 문제였다. Java 17·Spring Boot 3.2.5 코드에서 그 호출을 어떻게 묶었는지 따라가 봤다.

## A가 조회하는 동안 B도 들어오면

캐시가 비어 있어서 A가 원본 조회를 시작했다고 하자. 응답이 오기 전에 B도 도착하면 B가 보는 캐시 역시 비어 있다. 그대로 진행하면 같은 방을 두 번 조회한다.

잠금으로 순서를 정하면 B를 기다리게 할 수 있다. 그런데 기다린 뒤에도 원본부터 읽으면 중복 조회는 남는다. A가 이미 채워 놓은 값은 두고 원본에 다시 다녀오는 셈이다. 기다린 보람이 없어진다.

| 순서 | A | B |
| --- | --- | --- |
| 1 | 캐시 없음 확인 | 캐시 없음 확인 |
| 2 | 잠금 획득, 원본 조회 | 같은 잠금 대기 |
| 3 | 값을 저장하고 잠금 해제 | 잠금 획득 |
| 4 | 응답 완료 | 캐시를 다시 읽어 저장된 값 반환 |

표의 마지막 줄이 중요하다. **B가 처음 확인한 결과와, 잠금을 얻은 뒤의 상태는 다를 수 있다.** 그래서 안쪽에서 한 번 더 읽어야 한다.

## 두 번째 get이 중복 호출을 막는다

실제 메서드에서 두 조회 부분만 발췌했다. 원본 조회와 캐시 저장은 마지막 주석 위치에서 이어진다.

```java
RoomStateSnapshot snapshot = roomStateCache.get(sessionId);
if (isFresh(snapshot)) {
    return snapshot.insufficientParticipants();
}

synchronized (lockFor(sessionId)) {
    RoomStateSnapshot refreshed = roomStateCache.get(sessionId);
    if (isFresh(refreshed)) {
        return refreshed.insufficientParticipants();
    }
    // 원본 조회와 캐시 저장이 이어진다.
}
```

바깥쪽 조회는 유효한 캐시가 있을 때 잠금을 기다리지 않고 반환하는 경로다. 안쪽 조회는 기다리는 사이 누군가 갱신했는지 확인하는 경로다.

캐시 조회까지 전부 잠그면 유효한 값만 읽을 요청도 줄을 서야 한다. 반대로 잠금 없이 조회하고 저장하면 여러 요청이 동시에 외부 호출을 시작한다. 두 번의 `get`은 **빠르게 읽는 경로와 한 번만 갱신하는 경로를 나눈 결과**다.

관련 테스트는 같은 세션을 여덟 요청이 동시에 조회하도록 구성돼 있다. 원본 역할을 하는 대역을 120ms 지연시키고, 호출 횟수가 한 번인지 검사한다. 이 테스트가 다루는 건 한 프로세스 안의 요청 합치기다. 실제 LiveKit 처리량을 측정한 결과는 아니다.

## 캐시를 오래 두면 해결될까

이 캐시는 서버 메모리에 있다. 서버가 두 대라면 각자 잠금을 잡고 원본을 읽을 수 있다. 여러 서버의 중복까지 막아야 할 때는 별도 조정이 필요하다.

같은 서버 안에서도 모든 세션이 독립적인 잠금을 갖지는 않는다. 코드는 64개 잠금 중 세션 ID의 해시로 하나를 고른다. 잠금 객체 수를 제한하는 대신, 서로 다른 세션이 같은 잠금을 기다릴 수 있다.

기본 캐시 수명은 1초다. 더 오래 두면 호출은 줄겠지만, 참가자가 나간 방을 한동안 정상으로 볼 수 있다. 이 값은 통화 세션을 유지할지 결정하는 데 쓰이므로, 조회 비용과 함께 오래된 판단의 비용도 봐야 한다.

이 메서드에서 먼저 볼 것은 `get`의 횟수보다 **두 조회 사이에 무엇이 바뀔 수 있는가**다. 잠금을 기다리는 코드라면 같은 질문을 해볼 만하다.
