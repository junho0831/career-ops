실패한 태스크를 다시 실행하는 버튼은 간단하다. 어려운 쪽은 이미 끝난 작업과 아직 안 끝난 작업을 구분하는 일이다. 파일 업로드는 성공했는데 데이터베이스 저장이 실패했다면, 재시도는 처음 실행과 다른 상태에서 시작한다.

기존 글에는 재실행으로 집계가 두 배가 되는 장애를 겪었다는 문장이 있었다. 그 경험을 입증할 로그는 없었다. 대신 이번에는 PythonStudy의 실제 DAG와 배치 실행 코드를 대조해, 확인할 수 있는 순서와 아직 보장되지 않는 부분을 나눠 적었다.

검토한 DAG는 한 시간 주기, 자동 과거 실행 비활성화, 동시 실행 한 개, 한 번의 재시도와 5분 대기를 설정한다. 이 숫자는 처리 성능을 측정한 결과가 아니라 소스에 있는 실행 정책이다. Airflow 배포 버전과 운영 실행 이력은 확인하지 않았으므로 아래 내용은 코드 검토와 재실행 설계에 한정한다.

## 같은 날짜가 같은 입력은 아니었다

DAG는 Python 호출에 날짜 문자열을 전달한다. 날짜를 업무 범위로 삼는 배치에서는 자연스러운 선택처럼 보이지만, 시간 단위 실행들이 같은 날짜를 전달할 수 있다는 점부터 살펴야 한다. 실행 횟수를 세는 것과 서로 다른 입력을 구분하는 것은 별개다.

더구나 날짜는 파일의 내용까지 고정하지 못한다. 같은 이름으로 파일이 교체되거나 늦게 도착한 데이터가 추가되면, 다음 실행이 보는 입력은 이전과 달라질 수 있다. 멱등성을 이야기하려면 같은 입력이라는 말이 날짜인지, 파일 버전인지, 이벤트 식별자인지부터 정해야 한다.

Airflow의 논리적 실행 시점은 버튼을 누른 현재 시각과 같다고 가정할 수 없다. 시간 구간을 처리하려는 태스크라면 구간 시작과 끝을 업무에 어떻게 전달할지 명시해야 한다. 날짜만 필요한 업무라면 어느 시간대의 날짜인지 정하고, 경계 시각에 들어온 입력도 같은 규칙으로 분류해야 한다.

읽어 본 DAG에는 시간대 지정이 있지만, 이것만으로 외부 파일의 시간 표기까지 일치한다는 증거는 되지 않는다. 파일명 시각, 원본 이벤트 시각, 데이터베이스 저장 시각 중 어느 값을 기준으로 묶는지 확인할 일이 남는다. 이 구분이 없으면 재시도 성공 뒤에도 다른 날짜의 자료가 섞일 수 있다.

실행 식별자와 업무 식별자를 나눠 두면 설명이 쉬워진다. 실행 식별자는 몇 번째 시도에서 무슨 일이 있었는지 추적하고, 업무 식별자는 같은 결과를 두 번 만들지 않도록 제한한다. 재시도 때 실행 식별자가 바뀌었다고 기존 업무 결과까지 새 항목으로 취급해서는 안 된다.

## 코드에서 확인한 세 개의 경계

결합 파일을 처리하는 경로는 결과 파일을 외부 저장소에 올린 뒤, 관련 데이터와 파일 매칭 정보를 데이터베이스 트랜잭션 안에 저장한다. 그 트랜잭션을 벗어난 다음 원본 파일을 삭제한다. 업로드와 삭제까지 데이터베이스 커밋에 포함되는 구조는 아니다.

이 순서를 따라가면 실패 위치를 세 곳으로 나눌 수 있다. 업로드 전에 실패하면 결과가 없을 수 있고, 업로드 뒤 저장 전에 실패하면 외부 파일만 남을 수 있다. 저장 뒤 원본 삭제에 실패하면 결과는 있는데 원본도 남아서 다시 발견될 수 있다.

특히 마지막 경우를 단순 실패로만 기록하면 다음 실행이 이미 저장된 데이터를 다시 처리할 수 있다. 원본이 존재한다는 사실만으로 미처리라고 판단할 수 없는 것이다. 원본 삭제는 처리 완료의 증거를 지우는 단계가 아니라, 완료 기록을 확인한 뒤 수행하는 정리 단계로 다루는 편이 낫다.

이 글에서 새로 제안하는 상태 구분은 준비 중, 결과 저장됨, 원본 정리 완료다. 실제 저장 모델이 이 세 상태를 그대로 갖고 있다는 뜻은 아니다. 업로드·커밋·삭제 사이의 틈을 설명하고, 재시도할 동작을 고르기 위한 설계 예시다.

결과 저장됨 상태에서 다시 시작하면 데이터 적재보다 결과 존재 여부와 원본 정리를 먼저 검증할 수 있다. 다만 파일이 있다는 것만으로 내용이 올바르다고 볼 수는 없다. 파일 크기나 체크섬, 입력 버전과 연결된 완료 기록처럼 결과를 구분할 근거가 함께 있어야 재사용 판단이 가능하다.

## 예외를 기록했다고 태스크가 실패하는 것은 아니다

실제 코드를 읽으며 가장 먼저 멈춘 부분은 재시도 설정이 아니었다. 개별 파일 처리에서 예외를 잡아 오류 수를 늘리고 계속 진행하는 경로가 있었고, 최상위 실행은 처리·건너뜀·오류 수를 출력한 뒤 끝났다. 오류가 한 건이라도 있으면 반드시 예외를 던지는 구조로 읽히지는 않았다.

Airflow는 하위 함수의 로그 문장만 보고 업무 실패를 추론하지 않는다. 호출이 정상 반환하면 스케줄러가 아는 결과와 업무에서 생각하는 결과가 달라질 수 있다. 그러면 재시도를 한 번 설정해 둬도 일부 파일 오류는 그 재시도 조건에 들어가지 못한다.

그렇다고 한 파일이 실패할 때마다 전체를 무조건 실패시키는 것만이 답은 아니다. 성공한 파일을 다시 읽어도 안전한지, 오류 파일만 별도로 재처리할 수 있는지에 따라 정책이 달라진다. 중요한 것은 부분 성공을 허용할지 결정하고, 그 결정을 반환값과 상태 저장에 드러내는 일이다.

예를 들어 처리 결과를 구조화해 반환하고, 복구 대상 오류가 남으면 호출부가 태스크를 실패로 종료하도록 바꿀 수 있다. 이것은 이번 글에서 배치 코드에 반영한 수정이 아니라 개선안이다. 그 전에 성공한 항목의 완료 기록을 믿고 건너뛸 수 있는지 테스트해야 전체 재시도가 안전해진다.

오류 종류도 나눌 필요가 있다. 일시적인 연결 실패에는 지연 후 재시도가 맞을 수 있지만, 형식이 잘못된 원본을 같은 파서에 계속 넣는다고 결과가 달라지지는 않는다. 영구 오류는 원본을 보존한 채 격리하고 원인과 처리 대상만 남기는 편이 재시도 폭주를 줄인다.

재시도 사이의 대기와 한 번의 작업 제한 시간도 서로 다르다. 외부 저장소 응답이 끝없이 지연되면 다음 시도를 기다리는 설정에는 도달하지 못한다. 연결·읽기 제한 시간과 태스크 전체의 종료 정책을 맞추고, 종료된 작업이 남긴 임시 파일을 다음 실행이 어떻게 식별할지 정해야 한다.

실행 제한 시간이 지났다고 외부 업로드까지 즉시 취소됐다고 단정할 수도 없다. 늦게 완료된 요청이 재시도 결과와 충돌할 수 있으므로, 결과를 확정할 때도 같은 업무 버전과 실행 소유권인지 확인할 장치가 필요하다. 이는 재시도 간격을 늘리는 것만으로 해결되지 않는 경계다.

## 한 트랜잭션으로 교체할 수 있는 범위

데이터베이스 안에서 특정 날짜의 집계를 다시 만드는 작업은 삭제와 적재를 같은 트랜잭션으로 묶는 방법을 검토할 수 있다. 아래는 소유한 집계 범위만 교체하는 개념 예제다. 실제 테이블 이름이나 운영 실행 결과를 옮긴 코드는 아니다.

```sql
BEGIN;
DELETE FROM daily_summary WHERE stat_date = :target_date;
INSERT INTO daily_summary (stat_date, account_key, amount)
SELECT :target_date, account_key, SUM(amount)
FROM raw_events
WHERE event_time >= :range_start AND event_time < :range_end
GROUP BY account_key;
COMMIT;
```

매개변수는 드라이버에서 바인딩하고, 중간 오류가 나면 연결의 롤백을 수행한다는 전제다. 삭제가 이미 커밋된 뒤 적재를 시작하는 구조와 달리, 적재 실패 시 같은 트랜잭션의 삭제도 되돌릴 수 있다. 외부 파일에 대한 부작용은 여전히 이 범위 밖이다.

같은 날짜를 두 작업이 동시에 교체하는 문제까지 해결된 것은 아니다. 업무 키에 대한 실행 소유권이나 데이터베이스 잠금처럼 겹치는 작업을 제어할 수단이 필요하다. DAG의 동시 실행 제한은 해당 DAG 실행을 제한하지만 수동 스크립트나 다른 DAG의 접근까지 막는 전역 잠금은 아니다.

원천 데이터가 계속 변경되는 상황에서는 최종 결과의 기준 시점도 정해야 한다. 같은 매개변수를 썼더라도 읽은 원본이 달라지면 결과가 달라지는 것이 정상일 수 있다. 같은 입력의 반복과 수정된 입력의 재계산을 구분해야 멱등성이 깨졌다는 판단도 정확해진다.

검토한 RAW 재적재 경로는 별도 주의가 필요했다. 대상 정리 뒤 청크별 적재가 이어지는 구조를, 날짜 전체가 한 번에 커밋되는 교체 방식이라고 설명할 수는 없었다. [청크 파이프라인 글](https://so-dak.com/pythonstudy-%eb%8c%80%ec%9a%a9%eb%9f%89-raw-%eb%a1%9c%ea%b7%b8-1973%eb%a7%8c-%ea%b1%b4-%ed%8c%8c%ec%9d%b4%ed%94%84%eb%9d%bc%ec%9d%b8-%ec%b5%9c%ec%a0%81%ed%99%94-%eb%93%80%ec%96%bc-%ec%8a%a4/)에서는 이 트랜잭션 범위를 따로 짚었다. 청크 처리와 원자적 교체는 서로 다른 요구다.

## UPSERT 전에 버전과 키부터

중복 행을 막는 고유 제약은 어떤 두 입력을 같은 업무로 볼지 데이터베이스에 표현하는 방법이다. 파일명만 쓸지, 파일 버전과 이벤트 순서를 함께 쓸지는 원천 데이터의 특성에 달려 있다. 서로 다른 정상 입력을 같은 키로 묶으면 중복 제거가 곧 데이터 유실이 된다.

기존 글은 이 설명 없이 ON CONFLICT 예제를 바로 제시했다. 하지만 함께 검토한 데이터 처리 코드에는 PostgreSQL 9.4를 전제로 하는 경로가 있다. 해당 문법은 9.5부터 지원하므로, 그 환경에 그대로 복사해서 쓸 해결책으로 적어서는 안 된다.

충돌 시 무시할지 갱신할지도 중요한 선택이다. 정정된 이벤트가 들어오는 서비스에서 무조건 무시하면 오래된 결과가 남는다. 무조건 갱신하면 늦게 도착한 옛 입력이 최신 결과를 덮을 수 있다. 버전이나 원본 수정 시각을 비교하는 규칙까지 있어야 키의 의미가 완성된다.

구버전에서 조회 후 삽입을 직접 조합하는 방법도 경쟁 조건을 고려해야 한다. 두 작업이 모두 미존재를 읽고 삽입할 수 있기 때문이다. 최종 고유 제약과 충돌 처리, 재조회 경로를 함께 설계하거나 실행 범위를 직렬화해야 하며, 문법만 바꾼 코드를 안전한 대체재로 소개하기는 어렵다.

파일 저장 역시 같은 관점으로 봤다. 재시도마다 새 이름으로 올리면 데이터베이스 중복은 막아도 외부 파일이 계속 쌓일 수 있다. 입력 버전으로 결정되는 경로와 임시 업로드 후 확정 절차를 검토할 수 있지만, 이름 변경의 원자성은 실제 저장소가 제공하는 동작을 확인한 뒤 기대해야 한다.

## 실패를 넣어 봐야 재실행 경계가 보인다

확인할 테스트는 성공 두 번보다 중간 실패 뒤 재실행이다. 업로드 직후, 데이터베이스 저장 직후, 원본 하나만 삭제된 직후에 각각 멈추게 하고 같은 업무를 다시 시작한다. 결과 행과 결과 파일, 남은 원본을 함께 비교해야 세 시스템 사이의 차이를 볼 수 있다.

원본 두 개를 순서대로 지우는 경로에서는 첫 삭제만 성공한 경우가 특히 중요하다. 재시도 시 한 파일이 없다고 전체 입력을 새 오류로 처리하면 완료된 결과까지 복구 대상에서 빠질 수 있다. 이미 확정된 매칭 기록을 기준으로 남은 정리를 이어갈 수 있는지를 확인할 테스트다.

완료 기록도 무조건 신뢰할 수는 없다. 외부 파일이 운영자의 정리나 보존 기간 때문에 사라질 수 있으므로, 이미 처리한 업무를 건너뛸 때 필요한 최소 결과가 남아 있는지 정책을 정해야 한다. 영구 보관해야 할 증거와 다시 만들 수 있는 중간 산출물을 구분하면 검증 비용을 줄일 수 있다.

동시에 두 번 시작하는 테스트와 늦게 도착한 입력 테스트도 별도로 필요하다. 반복 실행에서 행 수가 같아도 값이 덮여 쓰였을 수 있으므로, 개수뿐 아니라 업무 키별 내용까지 비교한다. 오류 로그에는 원본 자료나 자격 증명 대신 재처리할 업무를 식별할 안전한 값만 남긴다.

배포 후 문제가 생겼을 때는 자동 재시도를 늘리기 전에 새 실행을 제한하고 마지막으로 확정된 단계를 확인하는 편이 낫다. 이미 삭제된 원본을 되돌릴 수 있는지, 미확정 업로드를 어떻게 정리할지까지 복구 절차에 들어가야 한다. 스케줄을 중지하는 것만으로 진행 중 작업의 부작용이 취소되지는 않는다.

이번 검토에서 남긴 다음 과제는 명확하다. 부분 오류를 호출부에 전달하는 방식과, 저장을 마친 뒤 원본 삭제만 남은 작업을 복구하는 테스트다. 재시도 횟수를 정하는 일은 그 두 가지를 설명할 수 있게 된 다음이다.
