로그인 버튼을 눌러 사용자 정보가 보이면 인증 기능이 끝난 것처럼 느껴진다. 하지만 그 화면을 다시 열었을 때, 여러 요청이 동시에 만료된 토큰을 보냈을 때, 갱신 응답을 받기 전에 연결이 끊겼을 때도 같은 설명이 가능한지는 다른 문제다.

VoiceLink의 인증 코드를 다시 읽으며 [로그인 성공](https://so-dak.com/%ec%a7%81%ec%9e%a5%ec%9d%b8-%eb%a7%a4%ec%b9%ad-%ec%84%9c%eb%b9%84%ec%8a%a4-redis-ttl%ec%9d%84-%ed%99%9c%ec%9a%a9%ed%95%9c-%eb%b9%84%eb%8f%99%ea%b8%b0-%ec%9d%b4%eb%a9%94%ec%9d%bc-%ec%9d%b8%ec%a6%9d/)보다 그다음 요청을 따라갔다. 서버는 Spring Boot 3.2.5와 JWT 라이브러리 jjwt 0.12.5를 사용하고, Flutter 클라이언트는 Dio 인터셉터에서 갱신을 처리한다. 여기서 다루는 것은 확인한 구현과 실패 가능 조건이며 실제 계정 사고나 공격 대응의 회고는 아니다.

기존 소셜 로그인 글과 JWT 글은 이 흐름을 따로 설명해서, 어디서 발급된 값이 어디에 쓰이는지 이어 읽기 어려웠다. 두 내용을 합치면서 제공자 로그인, 서비스의 로그인 교환 코드, 서비스 API용 토큰을 구분하는 것부터 시작했다.

## 콜백에 넘기는 것은 최종 토큰이 아니다

소셜 로그인 성공 처리에서는 사용자를 찾은 다음 짧게 살아 있는 코드를 발급한다. 코드와 사용자 식별자의 대응을 Redis에 저장하고, 클라이언트 콜백 주소의 fragment에 코드를 붙여 이동시킨다. 클라이언트는 이 코드를 서버에 교환해 서비스용 토큰을 받는다.

이 코드는 제공자가 발급한 OAuth 인가 코드와 구분해야 한다. 외부 로그인 절차가 끝난 뒤 서비스 내부에서 추가로 만든 교환 코드다. 이름이 비슷하다고 두 값의 발급자나 검증 위치가 같다고 설명하면, 어느 구간을 보호하는 장치인지 헷갈리게 된다.

코드를 소비하는 경로는 Redis에서 값을 읽으면서 삭제한다. 같은 코드를 두 번 교환하는 상황에서 단순 조회 후 별도 삭제보다 소비 경계가 명확하다. 다만 읽어 삭제한 뒤 사용자 조회나 응답 생성이 실패하면, 처음 요청은 완료되지 않았어도 코드가 이미 사라졌을 수 있다.

이때 같은 코드를 끝없이 재전송하는 복구는 맞지 않는다. 코드가 만료되었거나 이미 소비되었다는 상태를 클라이언트가 구분 가능한 오류로 처리하고 로그인 시작점으로 돌아갈 수 있어야 한다. 일회성은 보안을 위한 제한인 동시에 사용자에게 복구 동작이 필요한 이유가 된다.

fragment는 일반적인 HTTP 요청 경로에 그대로 전송되지 않는다는 이점이 있지만, 브라우저 스크립트가 읽을 수 있는 값이다. 이것만으로 유출 가능성이 사라지지는 않는다. 코드를 읽은 뒤 주소에서 제거하는 처리, 콜백 주소의 허용 범위, 화면 분석 도구가 주소를 수집하는지까지 별도로 점검할 대상이다.

또한 교환 코드가 있다고 해서 OAuth의 state 검증이나 리디렉션 검증을 대체할 수는 없다. 각각 다른 요청과 대상을 묶는 장치이기 때문이다. 이 글의 소스 검토만으로 로그인 전체의 보안 검증이 완료되었다고 말하지 않고, 코드가 맡은 역할까지만 설명하는 이유다.

## API 토큰과 갱신 토큰의 수명이 다르다

서비스의 액세스 토큰에는 사용자 식별자와 발급·만료 시각 등이 들어가고 서버 서명을 붙인다. 요청 필터는 토큰을 검증한 뒤 사용자를 조회해 인증 정보를 만든다. 서명 검증은 값이 바뀌지 않았는지를 확인하는 과정이며, 내용이 암호화되어 보이지 않는다는 의미는 아니다.

따라서 토큰 내용에 비밀번호나 민감한 사용자 자료를 넣어서는 안 된다. 로그와 오류 추적에서도 원문 토큰을 남길 이유가 없다. 요청을 추적하려면 토큰 전체 대신 별도의 요청 식별자와 최소한의 결과 상태를 사용하는 편이 낫다.

리프레시 토큰은 별도로 만든 무작위 값이다. 확인한 서버 구현은 원문을 그대로 Redis 키로 쓰지 않고 해시를 계산해 사용자와 연결하며, 만료 시간을 함께 둔다. 토큰 해시는 조회 키를 보호하는 일부 수단이지, 저장소 접근 권한이나 전송 구간 보호를 대신하지 않는다.

액세스 토큰의 만료 시간과 리프레시 토큰의 만료 시간은 서로 다른 정책이다. 전자는 API 요청 자격이 유효한 시간을 정하고 후자는 다시 발급받을 수 있는 기간을 정한다. 긴 갱신 기간을 선택할수록 기기 분실이나 계정 변경 시 어떤 세션을 폐기할지도 함께 설계해야 한다.

사용자 조회가 포함되는 코드에서는 토큰만 유효하더라도 사용자가 사라진 경우를 처리해야 한다. 반대로 사용자에게 권한 변화가 생겼을 때 어떤 정보가 매 요청 새로 읽히고 어떤 정보가 발급 당시 값으로 남는지도 중요하다. 서명이 맞는다는 조건 하나로 업무 권한 판단까지 끝나는 것은 아니다.

## 갱신 한 번에 성공과 소비를 묶을 수 있을까

현재 갱신 경로는 기존 리프레시 토큰에 해당하는 값을 읽으며 삭제하고, 사용자를 찾은 뒤 새 리프레시 토큰을 만든다. 이전 값을 계속 재사용하지 못하게 회전시키는 구조다. 핵심 순서를 줄이면 다음과 같다. 예외 처리와 검증은 원본 서비스에서 수행하며 아래는 흐름을 설명한 의사 코드다.

```text
기존 토큰의 해시로 사용자 참조를 읽고 삭제한다
참조가 없으면 갱신을 거절한다
유효한 사용자를 조회한다
새 갱신 토큰을 저장한다
새 액세스 토큰과 함께 응답한다
```

한 번 읽어 삭제하는 명령은 기존 토큰 소비의 경쟁을 줄인다. 그러나 그 명령부터 새 토큰 응답까지 전체가 하나의 원자적 작업이라는 뜻은 아니다. 데이터베이스 조회, 새 저장, HTTP 응답 사이에는 각각 실패할 수 있는 구간이 남는다.

예를 들어 서버가 새 토큰을 만들었지만 응답이 클라이언트에 도착하지 못하면, 클라이언트는 이전 토큰만 가진 채 남을 수 있다. 다시 갱신해도 이전 값은 이미 소비되었으므로 거절될 수 있다. 이 가능성은 서버 오류 로그가 없더라도 네트워크의 응답 유실만으로 생긴다.

여기에 재사용 유예를 추가하면 사용자 복구는 편해질 수 있지만 탈취된 이전 토큰도 허용하는 범위가 넓어진다. 요청 식별자와 응답 재사용 범위를 설계하는 방법도 있지만, 보존할 정보와 기기 식별의 신뢰성을 따져야 한다. 이번 글에서 그런 장치가 구현돼 있다고 주장하지 않았다.

이전 토큰의 재사용을 발견해 같은 로그인 계열 전체를 폐기하는 정책도 별도 기능이다. 현재 읽어 본 회전 서비스에서 한 번 소비된 값을 거절하는 것과, 모든 연관 토큰을 찾아 폐기하는 것은 같은 보장이 아니다. 구현한 범위와 보안 정책에서 원하는 범위를 문서에 따로 남길 필요가 있다.

## 동시에 받은 401은 한 번만 갱신하기

화면을 열 때 여러 API가 동시에 실행되면 액세스 토큰 만료도 여러 요청에서 함께 드러날 수 있다. 각 요청이 같은 리프레시 토큰으로 따로 갱신하면 한 요청만 소비에 성공하고 나머지는 실패할 수 있다. 서버의 일회성 정책이 클라이언트 동시성 문제로 나타나는 경우다.

Dio 구성에는 진행 중인 갱신 Future를 공유하는 변수가 있다. 이미 갱신이 진행 중이면 그 결과를 기다리고, 끝나면 공유 상태를 비운다. 한 Dio 인스턴스 안에서 겹친 요청들이 같은 갱신 결과를 이용하도록 만드는 장치다.

이 범위를 브라우저의 모든 탭이나 기기 전체로 넓혀 해석하면 안 된다. 별도 인스턴스와 별도 실행 문맥은 같은 메모리를 공유하지 않는다. 탭 여러 개가 같은 저장소의 토큰을 읽는 환경에서는 한쪽이 갱신한 뒤 다른 쪽이 이전 값을 쓰는 경우를 추가로 검증해야 한다.

갱신 후 원래 요청을 다시 보낼 때는 재시도 표시를 넣어 무한 반복을 막는다. 갱신 요청 자체가 또 갱신을 부르는 경로도 제외한다. 이 두 조건이 없으면 잘못된 자격 증명 하나가 반복 요청으로 늘어나서 실제 오류를 찾기 어려워진다.

원래 요청을 재전송해도 되는지도 확인할 일이다. 인증 단계에서 확실히 거절된 읽기 요청과, 처리 결과를 알 수 없는 변경 요청의 재시도는 다르다. 결제나 등록처럼 중복 부작용이 있는 API라면 업무 식별자와 서버의 멱등 처리 조건을 별도로 갖춰야 한다.

파일 스트림을 보낸 요청은 이미 소비한 본문을 그대로 다시 보낼 수 없는 경우도 있다. 인터셉터가 모든 요청을 같은 방식으로 재생할 수 있다고 가정하지 않고, 다시 만들 수 있는 본문인지 요청 단위로 판단하는 편이 안전하다. 인증 갱신과 업무 재시도를 하나의 기능으로 숨기지 않으려는 이유다.

## 저장과 로그아웃에서도 중간 상태가 생긴다

클라이언트는 보안 저장소 라이브러리에 액세스 토큰, 갱신 토큰, 사용자 표시 정보를 저장한다. 소스에서는 여러 키를 순서대로 쓰므로, 쓰기 중 실패했을 때 모든 값이 동시에 바뀌었다고 보장하는 형태는 아니다. 플랫폼 저장소 오류까지 포함한 복구는 별도 검증 대상이다.

새 액세스 토큰만 저장되고 갱신 토큰 저장이 실패하면 당장은 API가 동작해도 다음 갱신에서 문제가 드러날 수 있다. 읽어 온 인증 묶음이 완전한지 검사하고, 불완전하면 저장 상태를 정리해 다시 로그인하도록 처리하는 방식을 검토할 수 있다. 이는 현재 코드에 추가로 필요한 검증 항목이다.

웹과 모바일에서 같은 라이브러리를 호출하더라도 저장소의 보안 특성이 같다고 단정해서는 안 된다. 기기 잠금과 키 저장 방식, 브라우저의 스크립트 실행 환경이 다르다. 라이브러리 이름에 secure가 들어간다는 이유로 XSS나 기기 탈취의 영향을 모두 막았다고 표현하지 않았다.

서버의 로그아웃은 전달받은 리프레시 토큰을 폐기한다. 이 동작은 앞으로의 발급을 막는 데 관련되어 있고, 이미 발급된 액세스 토큰을 즉시 모든 서버에서 무효화하는 별도 차단 목록은 해당 서비스에서 확인하지 못했다. 로그아웃이라는 한 단어 아래 서로 다른 수명이 남을 수 있다.

클라이언트 저장값 삭제와 서버 폐기는 어느 쪽이 실패할지도 나눠 봐야 한다. 네트워크가 끊긴 상태에서 화면상 로그아웃을 끝내더라도 서버 폐기가 성공한 것은 아닐 수 있다. 사용자에게 보여 주는 상태와 서버 세션의 유효성을 구분하고, 여러 기기 로그아웃이 필요하면 별도 세션 모델을 설계해야 한다.

## 검증할 때는 응답이 사라지는 구간부터

기존 단위 테스트에는 해시된 키와 만료 설정, 회전 시 기존 값 소비, 없는 토큰 거절, 폐기 호출을 확인하는 항목이 있다. 이 테스트가 확인하는 것은 서비스가 저장소에 요구한 동작이다. 실제 Redis 장애나 응답 유실을 재현한 결과까지 포함한다고 볼 수는 없다.

추가 검증은 동시 갱신에서 시작하는 편이 좋겠다. 같은 토큰으로 두 요청을 겹쳐 보내 소비 결과를 확인하고, 하나의 클라이언트에서는 갱신 호출이 합쳐지는지 본다. 이어서 서로 다른 클라이언트 실행 문맥을 사용해 메모리 공유의 경계 밖에서도 오류 처리가 일관적인지 확인한다.

다음은 새 토큰 저장 직후 응답을 끊는 경우다. 사용자가 어떤 저장값을 가진 채 남는지, 다시 로그인할 수 있는지, 실패한 갱신 때문에 화면이 반복 이동하지 않는지 확인해야 한다. 이때 기록할 것은 성공률을 꾸민 숫자가 아니라 각 실패 위치의 서버 상태와 클라이언트 상태다.

토큰 만료 시각 주변의 테스트에는 서버와 클라이언트 시계 차이도 포함한다. 클라이언트가 만료를 예상할 수 있더라도 최종 검증은 서버가 수행하며, 네트워크 지연 동안 유효 기간이 끝날 수 있다. 경계 시각을 고정한 테스트를 쓰면 우연한 실행 타이밍에 결과가 흔들리는 것을 줄일 수 있다.

실패 메시지도 사용자와 로그의 목적을 나눠야 한다. 화면에는 다시 시도하거나 로그인할 수 있는 동작을 보여 주고, 내부 기록에는 어느 단계가 실패했는지 남긴다. 원문 자격 증명과 외부 제공자의 전체 응답을 그대로 기록하는 방식은 문제를 분석하려다 새로운 노출을 만들 수 있다.

이번에 로그인 설명을 고치며 가장 달라진 것은 완료 지점이었다. 토큰을 발급했다는 사실보다, 다음 갱신이 실패했을 때 사용자가 어떤 상태로 남는지를 설명해야 인증 흐름이 끝난다. 다음 검증은 정상 로그인 화면보다 응답을 잃은 회전 요청부터 시작하려 한다.
