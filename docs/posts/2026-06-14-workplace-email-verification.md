회사 이메일로 코드를 받았다는 사실을 “재직 인증 완료”라고 보여 줘도 될까. 기능 구현보다 먼저 정해야 할 문구였다. 메일을 읽을 수 있다는 것과 지금 그 회사에 재직한다는 것은 같은 증거가 아니기 때문이다.

VoiceLink의 문서와 서버 코드는 이 절차를 회사 이메일 수신 확인으로 구분한다. [사용자의 수신 확인 상태](https://so-dak.com/spring-boot-redis-jwt-access-token%ea%b3%bc-opaque-refresh-token-%ec%95%88%ec%a0%84%ed%95%98%ea%b2%8c-%ea%b4%80%eb%a6%ac%ed%95%98%ea%b8%b0/)와 운영자의 도메인 검수 상태도 따로 둔다. 기존 글에서 인증이라는 말로 뭉뚱그렸던 내용을 이 두 상태를 중심으로 다시 풀었다.

검토 대상은 Spring Boot 3.2.5 서버의 발송·확인 서비스, Redis 임시 상태, 도메인 검수 코드와 단위 테스트다. 실제 메일 도착률이나 재직 검증 성능을 측정한 글은 아니다. 공개 문구도 코드가 확인할 수 있는 범위를 넘지 않도록 맞췄다.

## 코드 하나가 증명하는 범위

메일 확인 코드는 해당 주소로 전달된 값을 사용자가 입력할 수 있는지 확인한다. 메일 전달 규칙이나 공유 계정이 있을 수도 있고, 과거에 발급받은 계정에 여전히 접근할 수도 있다. 그래서 수신 확인만으로 개인 신분이나 현재 고용 관계까지 보증할 근거는 부족하다.

도메인 검수 역시 별개다. 도메인과 회사 표시명의 관계를 운영자가 검토할 수는 있지만, 그 도메인의 모든 계정이 동일한 조건의 구성원이라는 뜻은 아니다. 화면에는 수신 확인 여부와 검수된 표시명을 각각의 의미에 맞게 표현해야 한다.

공통 메일 서비스 도메인을 차단하는 목록은 입력 대상을 줄이는 정책이다. 차단 목록에 없다는 이유로 정식 회사 도메인이 되는 것은 아니며, 목록이 모든 개인용 도메인을 포함한다고 볼 수도 없다. 통과한 입력을 곧바로 신뢰 등급으로 바꾸지 않는 편이 정확하다.

현재 문서는 직장인 전용 매칭 큐 분리가 구현된 상태와도 구분한다. 확인 상태를 표시하는 기능과 확인된 사용자끼리만 매칭하는 기능은 서로 다르다. 라벨이 있다고 전용 매칭까지 제공한다고 설명하면 사용자 기대와 실제 동작이 어긋난다.

이 구분은 단순한 표현 수정에 그치지 않는다. 이후 재확인이나 도메인 차단 기능을 추가할 때 어떤 상태를 변경할지 결정하는 기준이 된다. 수신 확인이 취소된 것인지, 표시명 검수가 바뀐 것인지 분리되어야 영향 범위도 좁힐 수 있다.

## 발송 전에 입력을 같은 규칙으로 묶었다

서버는 동의 여부를 확인한 뒤 주소를 정리하고 형식을 검사한다. 앞뒤 공백과 일부 감싼 문자를 제거하며 대소문자를 정규화하는 정책을 사용한다. 데이터베이스에서 같은 주소를 찾는 쿼리도 이 정책과 일치해야 중복 판단이 흔들리지 않는다.

다만 모든 메일 제공자의 주소 의미가 같지는 않다. 점을 없애거나 더하기 뒤의 문자열을 지우는 식의 보정은 해당 서비스의 규칙을 일반화할 수 있어 이번 설명에 넣지 않았다. 프로젝트가 채택한 정규화 정책과 이메일 표준의 모든 예외를 처리했다는 주장은 구분할 필요가 있다.

발송 대상은 로그인한 사용자와 주소를 함께 묶는다. 다른 계정이 확인한 주소인지, 이미 확인을 마친 사용자인지도 검사한다. 이 검사는 화면에서 버튼을 숨기는 것보다 서버에서 수행되어야 요청을 직접 보낸 경우에도 같은 규칙을 적용할 수 있다.

이어서 도메인 검수 기록을 준비하고 확인 코드와 임시 상태를 만든다. 사용자가 입력한 회사명 후보는 운영자가 승인한 이름과 구분해 보관한다. 사용자가 쓴 문자열을 바로 상대에게 검수된 회사명으로 보여 주면 별도 검수 상태를 둔 의미가 사라진다.

주소 입력을 잘못한 경우에는 원래 요청과 바뀐 주소를 혼동하지 않아야 한다. 발송 후 입력창을 바꿨다면 어떤 주소로 보낸 코드를 확인하는지 화면에 분명히 남겨야 한다. 서버가 주소를 함께 검증하더라도 화면 설명이 빠지면 사용자는 도착한 코드가 계속 틀린다고 느낄 수 있다.

## 유효 시간과 재전송 대기는 다른 상태다

기본 설정에는 여섯 자리 숫자 코드, 300초 유효 시간, 다섯 번 확인 시도, 60초 재요청 대기가 들어 있다. 이는 현재 설정에서 읽은 정책 값이며 모든 서비스에 권장하는 보안 기준은 아니다. 실제 요청량과 전달 지연을 본 뒤 조정해야 할 값이다.

코드 생성에는 보안용 난수 생성기를 사용하고, 저장할 때는 주소와 코드를 조합한 해시를 둔다. 짧은 숫자 코드의 경우 해시만으로 온라인 추측 시도를 막을 수는 없다. 유효 시간과 시도 제한, 발송 제한을 함께 두는 이유가 여기에 있다.

확인 상태와 재전송 대기는 서로 다른 키로 관리된다. 사용자가 잘못 입력했을 때 실패 횟수를 늘리더라도 남은 유효 시간을 그대로 사용하려는 경로가 있다. 잘못된 입력을 할 때마다 코드 수명이 새로 시작되면 원래 만료 정책과 달라지기 때문이다.

재전송은 사용자 입장에서 같은 버튼이지만 기존 코드의 의미를 바꿀 수 있다. 같은 주소의 임시 상태를 새 코드로 덮으면 이전 메일의 코드는 더 이상 맞지 않는다. 여러 메일이 늦게 섞여 도착할 수 있으므로, 가장 최근 요청 기준으로 확인한다는 안내가 필요하다.

코드 유효 시간은 서버 저장소의 만료가 기준이고 화면의 타이머는 안내다. 앱이 백그라운드에 갔다가 돌아오면 타이머 표시와 실제 남은 시간이 다를 수 있다. 화면에 시간이 남아 보여도 서버가 만료로 거절할 수 있다는 경로를 오류가 아니라 상태 변화로 처리해야 한다.

발송 요청 제한과 코드 확인 제한도 따로 본다. 메일을 많이 보내는 문제와 짧은 코드를 많이 추측하는 문제는 자원을 쓰는 위치가 다르다. 계정 하나의 대기만으로 여러 계정에서 같은 주소에 요청하는 상황까지 해결됐다고 말할 수는 없다.

## 메일 발송과 데이터 저장은 한 번에 끝나지 않는다

소스는 임시 상태를 저장한 다음 메일을 보낸다. 메일 라이브러리가 발송 예외를 던지면 임시 상태와 대기를 지우고 오류를 돌려준다. 사용자에게 도착하지 않을 코드를 확인하라고 요구하지 않기 위한 보상 처리다.

여기서 메일 발송 함수가 정상 반환했다는 것과 수신함에 도착했다는 것은 구분해야 한다. 중간 메일 서버가 받아도 이후 전달 실패나 스팸 분류가 있을 수 있다. 서버의 발송 완료 로그를 실제 수신 성공률로 바꿔 적지 않은 이유다.

반대로 서버가 실패 응답을 받았더라도 메일은 전달될 수 있는 경계도 있다. 외부 시스템의 응답이 유실되면 성공 여부를 모르는 상태가 되기 때문이다. 이 경우 지워진 임시 상태에 해당하는 메일이 나중에 도착할 수 있고, 사용자가 재요청할 수 있는 흐름이 필요하다.

확인 성공 쪽은 사용자 상태를 데이터베이스에 저장한 뒤 Redis 임시 상태를 정리한다. 데이터베이스 트랜잭션이 Redis와 SMTP까지 함께 되돌리는 것은 아니다. 어느 단계의 실패가 무엇을 남기는지 나눠 설명해야 재시도 정책도 결정할 수 있다.

예를 들어 확인 응답을 받지 못한 사용자가 같은 요청을 다시 보내면, 이미 확인된 사용자라는 이유로 거절될 수 있다. 화면에서는 현재 사용자 상태를 다시 조회해 성공이 반영되었는지 확인하는 복구가 필요하다. 응답 코드 하나만 보고 발송부터 다시 시작하면 완료된 작업을 반복할 수 있다.

## 중복 주소와 동시 요청은 마지막 저장까지 본다

다른 사용자가 이미 확인한 주소인지는 발송 시점과 완료 시점에 다시 검사한다. 발송 뒤 코드 입력까지 시간이 지나므로 앞선 조회 결과만 믿을 수 없기 때문이다. 그 사이 다른 계정의 확인이 먼저 끝날 수 있다.

조회 후 저장 사이에도 틈은 남는다. 그래서 주소의 고유 제약처럼 최종 데이터베이스 규칙이 필요하고, 실제 서비스에는 저장과 flush에서 충돌을 처리하는 경로가 있다. 읽어 보고 없으면 저장한다는 순서만으로 동시 중복이 불가능하다고 설명해서는 안 된다.

시도 횟수도 같은 관점으로 검증해야 한다. 현재 임시 상태 저장소는 값을 읽고 바꿔 쓰는 메서드로 구성되어 있다. 두 확인 요청이 겹쳤을 때 실패 횟수 증가가 보존되는지, 재발송과 확인이 겹쳐 이전 상태를 덮지 않는지는 단위 호출의 성공과 다른 테스트 대상이다.

재요청 대기 확인과 저장도 여러 명령으로 나뉘어 있다. 버튼 연타를 화면에서 막는 것은 사용자 경험에 도움이 되지만, 서버에서 동시에 들어온 요청의 원자성을 증명하지는 않는다. 필요하면 조건부 저장이나 짧은 원자적 연산으로 묶는 개선을 검토해야 한다.

이 글은 그 경합을 실제 운영 장애로 확인했다고 주장하지 않는다. 메서드가 나뉜 구조에서 어떤 결과를 추가로 시험해야 하는지 짚은 것이다. “Redis를 썼으니 중복 요청이 막혔다”는 설명보다 보호 범위가 어디까지인지 적는 편이 다음 검증에 도움이 된다.

## 상대에게 보여 주는 정보는 더 좁다

도메인 검수가 승인되면 등록된 회사 표시명을 우선 사용할 수 있다. 차단된 도메인은 상대에게 표시하지 않는 경로가 있고, 그 외 상태는 승인된 회사명과 구분해 처리한다. 사용자의 메일 확인 상태가 남아 있어도 도메인 상태에 따라 표시가 달라질 수 있다.

거절과 차단도 의미가 같지 않다. 표시명 검수가 거절되었다는 이유만으로 과거의 메일 수신 사실이 사라지는 것은 아니다. 차단은 추가 확인과 정보 표시를 제한하는 운영 판단이므로, 두 상태를 하나의 실패 라벨로 뭉치지 않는 편이 변경 이유를 설명하기 쉽다.

상대에게 전체 이메일 주소를 보여 줄 필요는 없다. 매칭 화면이 요구하는 것은 서비스가 정한 표시 정보이며, 확인을 위해 수집한 주소를 그대로 공개할 이유와는 다르다. 로그도 마스킹된 값을 사용하지만 예외 객체나 외부 메일 응답에 원문이 포함되는지는 별도로 살펴야 한다.

관리자 검수 권한은 서버에서 검사하고, 설정에 없는 사용자는 거절한다. 관리자 화면을 숨기는 것과 관리자 API 접근을 제한하는 것은 별개다. 검수 상태를 바꾸는 요청에서는 변경 대상과 변경자, 변경 시점을 남겨야 잘못된 표시를 되돌릴 때 근거가 생긴다.

수집에 동의했다는 확인과 데이터 보존 정책도 같은 것은 아니다. 어떤 목적으로 주소를 저장하고 언제 삭제할지, 확인 상태를 잃었을 때 다시 확인할지 같은 운영 정책은 따로 정해야 한다. 여기서는 법적 적합성을 판정하지 않고 코드와 화면에 드러나는 정보 범위만 다뤘다.

## 테스트에서 확인한 것과 더 볼 것

서비스 테스트에는 동의 없는 요청, 공통 도메인, 이미 사용 중인 주소, 재요청 대기, 메일 발송 실패를 확인하는 항목이 있다. 확인 성공 시 사용자 상태를 바꾸고 임시 상태를 지우는지, 틀린 코드가 시도 횟수에 반영되는지도 검사한다. 이는 서비스 규칙을 확인하는 근거다.

실제 SMTP 전달과 Redis 만료 타이밍은 테스트 대역만으로 확인되지 않는다. 검증용 수신함과 격리된 저장소에서 늦게 도착한 메일, 만료 직전 입력, 재전송 직후 옛 코드 입력을 나눠 시험할 필요가 있다. 주소와 코드는 공유 가능한 테스트 값만 사용해야 한다.

동시 완료 테스트에서는 같은 주소를 두 계정이 함께 확인하려는 상황을 재현한다. 데이터베이스에 최종 한 계정만 연결되는지와 실패한 쪽의 화면 복구를 함께 본다. 단지 예외가 났다는 것보다 잘못된 확인 상태가 남지 않는 것이 중요한 결과다.

관리자 상태 변경도 사용자 흐름 안에서 검증해야 한다. 코드를 발송한 뒤 도메인이 차단되면 확인이 제한되는지, 이미 연결된 상대 표시가 언제 갱신되는지 확인한다. 상태가 바뀐 뒤 오래된 캐시가 표시를 계속 유지한다면 저장소의 값만 맞아도 화면은 잘못될 수 있다.

이번에 가장 먼저 고친 문장은 기능 이름이었다. “회사 인증”이라고 크게 묶기보다 “회사 이메일 확인”이라고 좁히니 코드가 보장해야 할 범위도 분명해졌다. 다음 확인은 더 강한 라벨을 붙이는 일이 아니라, 만료와 재전송이 겹쳐도 그 라벨의 의미가 유지되는지 보는 일이다.
