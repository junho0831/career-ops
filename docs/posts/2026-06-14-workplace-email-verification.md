회사 이메일 확인에 체크 표시 하나를 붙이려면, 먼저 그 표시가 무엇을 보장하는지 정해야 한다.

설명용 주소 `member@example.org`로 보낸 코드를 맞혔다고 하자. 확인된 것은 메일을 받을 수 있다는 사실이다. 메일함 열쇠가 재직증명서는 아니다. 입력한 회사 이름까지 맞다고 볼 수도 없다.

VoiceLink 문서는 이 차이를 기능의 범위로 정한다. **사용자의 메일 수신 확인과 도메인의 회사명 승인은 별도 상태다.**

```mermaid
flowchart TD
 E["회사 이메일 입력"] --> C["코드 발급<br/>메일 전송"]
 C --> V{"유효한 코드인가"}
 V -->|예| M["이메일 수신 확인"]
 V -->|만료 또는 오답| U["미확인 유지"]
 D["도메인 검토"] --> A["승인 / 검토 중"]
 M --> P["화면의 확인 정보"]
 A --> P
```

한 사용자가 코드를 맞혀도 회사명은 검토 중일 수 있다. 반대로 도메인이 승인돼 있어도 처음 온 사용자는 자신의 코드를 확인해야 한다. 상태를 하나로 합치면 어느 쪽이 끝났는지 잃어버린다.

이 기능은 메일 확인과 표시 정보 관리까지다. 재직 증빙이나 직장인 전용 매칭 큐 분리까지 구현한 것은 아니다.

## 먼저 도착한 메일이 최신 코드는 아닐 수 있다

코드 발급에는 세 가지 제한이 있다. 모두 “기다리는 시간”처럼 보여도 막으려는 행동이 다르다.

| 제한 | 현재 기본값 | 판단하는 질문 |
| --- | --- | --- |
| 코드 유효 시간 | 300초 | 이 코드로 아직 확인할 수 있는가 |
| 재전송 대기 | 60초 | 새 메일을 다시 요청해도 되는가 |
| 확인 시도 횟수 | 5회 | 같은 발급 건에서 더 확인할 수 있는가 |

발송을 반복하는 요청과 짧은 코드를 계속 찍어 보는 요청을 같은 제한으로 다루기는 어렵다. 코드 수명, 재전송 간격, 오답 횟수를 각각 두는 이유다.

첫 메일이 늦어서 1분 뒤 새 코드를 요청했다고 해보자. 새 임시 상태로 바뀐 뒤 옛 메일이 도착하면, 사용자는 방금 받은 코드를 넣고도 틀렸다는 안내를 받을 수 있다.

따라서 화면은 “다시 보내기까지 남은 시간”과 “현재 코드의 유효 시간”을 구분해야 한다. **만료 판단은 서버가 하고 카운트다운은 안내만 한다.** 앱을 백그라운드에 뒀다가 돌아왔다고 코드 수명이 늘어나지는 않는다.

## 메일을 보냈다는 기록만으로 완료할 수 없는 이유

서비스는 Redis에 확인할 임시 상태를 저장한 다음 메일을 보낸다. 발송 호출이 실패하면 임시 상태를 정리한다. 발송 함수가 정상 반환해도 실제 수신함 도착까지 확인된 것은 아니다. 반대로 외부 메일 시스템이 요청을 받았어도 응답이 유실되면 호출은 실패할 수 있다.

코드를 맞힌 뒤에는 다른 경쟁이 생긴다. 발급 시점에 비어 있던 주소를 다른 계정이 먼저 등록할 수 있다. 확인 완료 시 중복을 다시 조회하고, DB 고유 제약으로 최종 저장까지 막아야 “한 주소는 한 계정” 규칙이 유지된다.

이때 DB 사용자 저장과 Redis 임시 상태 삭제는 하나의 원자적 작업이 아니다. 두 계정의 동시 완료나 중간 실패는 서비스 분기 테스트를 넘어 실제 DB·Redis에서 확인할 부분이다.

표시 문구는 구현이 확인한 만큼만 좁혀야 한다. “재직 인증 완료” 대신 **“회사 이메일 확인 완료”**, 승인된 도메인에는 검수된 회사명을 보여 주는 식이다. 체크 하나를 위해 서로 다른 사실을 합칠 필요는 없다.
