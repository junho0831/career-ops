테스트 결과는 성공이었지만 한 항목은 실행되지 않았다. 이번 글을 고치면서 관련 백엔드 테스트를 돌렸을 때 나온 결과다. 전체 명령이 성공으로 끝났다는 것과 준비한 모든 검증이 수행되었다는 것은 같지 않았다.

2026년 9월 22일 VoiceLink의 인증·매칭·Outbox·사용자 안전·통화 품질 등 관련 테스트를 선택해 실행했다. 결과 파일에는 17개 테스트 묶음, 총 80개 항목 중 79개 통과와 1개 건너뜀이 기록되었다. 건너뛴 항목은 실제 PostgreSQL 컨테이너에서 잠금 경쟁을 확인하는 테스트였다.

이 결과를 출발점으로 기존 단위 테스트 글과 Testcontainers 글을 합쳤다. 환경은 Java 17 기반 Spring Boot 3.2.5 프로젝트이며, 아래 내용은 선택 실행한 범위에 대한 기록이다. 모든 기능과 운영 환경을 검증했다거나 실제 기기 통화까지 성공했다는 의미는 아니다.

## 테스트 이름보다 경계를 먼저 본다

단위 테스트와 통합 테스트를 구분할 때 어노테이션 이름만 보는 것은 충분하지 않았다. 실제로 실행한 구성 요소와 대신 바꾼 의존성이 무엇인지 봐야 한다. 클래스 하나를 테스트하더라도 실제 저장소를 연결했다면 확인하는 경계가 달라진다.

테스트 대역은 외부 의존성의 특정 응답을 통제하는 데 유용하다. 사용자를 찾지 못했을 때 거절하는지, 토큰을 소비한 뒤 새 값을 저장하는지 같은 서비스 규칙을 빠르게 확인할 수 있다. 다만 가짜 저장소가 반환하도록 적은 값을 실제 데이터베이스가 그대로 반환한다는 증거는 아니다.

Stub과 Mock이라는 이름도 객체의 종류를 영원히 나누는 이름으로 외우기보다 테스트에서 맡은 역할로 읽는 편이 낫다. 정해진 응답을 주는 데 쓰는지, 중요한 외부 호출을 검증하는 데 쓰는지에 따라 역할이 달라진다. 도구 하나로 둘 다 표현할 수도 있다.

호출 횟수 검증은 그 횟수가 요구일 때 의미가 있다. 같은 결과를 만드는 내부 메서드가 둘로 나뉘었다고 깨지는 테스트는 리팩터링 비용만 높일 수 있다. 반면 같은 토큰을 두 번 소비하지 않는지나 외부 발송을 불필요하게 반복하지 않는지는 중요한 업무 경계다.

결국 먼저 적을 질문은 무엇이 틀리면 이 테스트가 실패해야 하는가다. 내부 구현을 그대로 복사한 기대값만 두면 코드와 테스트가 같은 실수를 공유할 수 있다. 입력과 최종 상태, 금지된 부작용처럼 사용자나 다른 시스템이 관찰할 수 있는 성질을 우선했다.

## 저장소 대역으로 SQL 잠금을 증명할 수 없다

[Outbox는](https://so-dak.com/%eb%b6%84%ec%82%b0-%ec%8b%9c%ec%8a%a4%ed%85%9c-%ec%a0%95%ed%95%a9%ec%84%b1-%eb%b3%b4%ec%9e%a5-transactional-outbox-pattern%ec%9c%bc%eb%a1%9c-%eb%a7%a4%ec%b9%ad-%ec%9d%b4%eb%b2%a4%ed%8a%b8-%eb%b0%9c/) 여러 발행자가 작업을 선점하는 구조이므로 같은 행을 동시에 처리하지 않는지가 중요하다. 저장소 메서드가 정해진 행을 반환하도록 설정한 단위 테스트는 서비스 분기를 확인할 수 있다. 실제 두 트랜잭션이 같은 테이블에 접근했을 때의 잠금은 확인하지 못한다.

프로젝트에는 PostgreSQL 16 컨테이너를 사용하는 저장소 테스트가 별도로 있다. 첫 번째 트랜잭션이 행을 잠근 채 기다리는 동안 두 번째 트랜잭션이 다른 행을 선점하는지 검사한다. H2에서 쿼리가 실행되었다는 결과와 구분할 필요가 있는 부분이다.

데이터베이스마다 SQL 문법과 잠금, 격리 수준의 동작이 다르다. 테스트용 데이터베이스가 운영과 다른데 단순 조회만 확인했다면 통합 테스트라는 이름을 붙여도 확인 범위는 제한적이다. 어떤 동작에서 실제 엔진이 필요한지 골라 사용하는 편이 비용과 신뢰를 함께 관리하기 쉽다.

이 저장소 테스트는 Docker를 사용할 수 없으면 건너뛰도록 설정되어 있다. 이번 선택 실행에서도 건너뜀으로 기록되었으므로 PostgreSQL 잠금 동작을 이번 실행에서 확인했다고 쓰지 않았다. 명령의 종료 코드만 보면 놓칠 수 있는 차이다.

중요한 통합 테스트라면 CI에서 건너뛰기를 실패로 볼지 정책을 정해야 한다. 개발자의 빠른 로컬 실행에서는 허용하더라도 배포 검증에서는 해당 환경을 반드시 제공하는 선택이 가능하다. 같은 테스트 설정을 모든 실행 목적에 그대로 쓰는 것이 최선은 아닐 수 있다.

컨테이너 사용 자체도 운영과 완전히 같은 환경을 뜻하지 않는다. 버전, 확장, 데이터 크기, 접속 수와 네트워크 지연은 별도 조건이다. 일회용 데이터베이스는 반복 가능한 출발점을 만드는 데 도움을 주지만 운영 재현의 모든 조건을 자동으로 채우지는 않는다.

## 동시성 테스트는 우연히 겹치기를 기다리지 않는다

두 스레드를 시작하고 잠깐 잠드는 테스트는 실행 순서가 환경에 따라 달라질 수 있다. 느린 CI에서는 아직 첫 단계에 도달하지 않았고, 빠른 환경에서는 이미 둘 다 끝났을 수 있다. 타이밍을 운에 맡기면 실패를 재현하기 어렵다.

확인한 PostgreSQL 테스트는 latch를 사용해 첫 작업이 잠금을 잡았다는 신호를 보낸 뒤 두 번째 작업을 시작한다. 해제 신호를 주기 전까지 첫 트랜잭션을 유지하므로, 검증하려는 경쟁 구간이 명시적으로 만들어진다. 단순 병렬 실행보다 무엇이 겹치는지 설명하기 쉽다.

아래는 그 의도를 줄인 의사 코드다. 실제 테스트의 트랜잭션 생성과 제한 시간 처리는 생략했지만, 두 작업의 순서와 관찰할 결과를 분리했다.

```text
작업 A: 별도 트랜잭션 시작 → 첫 행 잠금 → 준비 신호 → 해제 신호 대기
작업 B: 준비 신호 확인 → 별도 트랜잭션에서 다음 행 선점
검증: B가 제한 시간 안에 끝나고 A와 다른 행을 선택
정리: A의 대기를 풀고 두 작업·실행기를 종료
```

대기에는 제한 시간이 있어야 한다. 실패한 테스트가 영원히 기다리면 원인보다 CI 자원 고갈이 먼저 문제가 된다. 검증 중 예외가 나더라도 다른 작업의 대기를 풀고 실행기를 정리할 수 있는지 확인해야 다음 테스트에 영향이 남지 않는다.

또한 작업마다 별도 트랜잭션이 필요하다. 테스트 메서드의 트랜잭션에 데이터를 아직 커밋하지 않았다면 다른 스레드가 그 행을 보지 못할 수 있다. 테스트의 격리 장치가 검증하려는 경쟁 상황 자체를 바꾸지 않도록 준비 데이터의 커밋 시점을 명확히 한다.

취소와 매칭 확정처럼 여러 단계가 경쟁하는 기능도 같은 방식으로 접근할 수 있다. 후보를 선점한 뒤 멈추고 취소를 넣은 경우와, 세션 저장 뒤 취소를 넣은 경우는 다른 시나리오다. 스레드 수를 늘리는 것보다 어느 경계를 끊어 보는지가 먼저다.

## 빠른 테스트가 놓치는 실패도 이름을 붙인다

토큰 회전 테스트는 저장소에서 기존 값을 소비하고 새 값을 만드는 호출을 확인한다. 그러나 새 토큰을 만든 뒤 응답이 유실되는 상황은 별도 검증이 필요하다. 서버 상태와 클라이언트가 가진 값이 달라지는 경계는 서비스 메서드 반환값만으로 드러나지 않는다.

Outbox도 마찬가지다. 발행 함수가 예외를 던졌을 때 재시도 상태를 기록하는 테스트와, 브로커에는 전달되었는데 확인 응답만 유실된 테스트는 다르다. 후자는 중복 전달 가능성을 포함하므로 최종 업무 결과가 한 번만 반영되는지를 함께 봐야 한다.

테스트 대역이 항상 즉시 응답하면 느린 의존성 때문에 발생하는 작업자 포화도 놓칠 수 있다. 외부 호출이 끝나지 않는 경우와 제한 시간 뒤 늦게 끝나는 경우를 나눠 넣는다. 제한 시간을 설정했다는 사실과 실제 요청이 취소되었다는 사실이 다른지도 여기서 드러난다.

저장소 예외를 잡는 코드에서는 예외 시점도 중요하다. 가짜 저장소가 save 호출에서 바로 실패하게 만드는 테스트만 있으면 실제 flush나 커밋 시점에 실패하는 동작을 놓친다. JPA 트랜잭션의 최종 결과를 확인해야 하는 이유다.

모든 실패를 하나의 거대한 E2E 테스트에 넣을 필요는 없다. 규칙은 작은 테스트에서 확인하고, 라이브러리와 저장소의 경계는 통합 테스트에서 확인하며, 사용자 흐름은 적은 수의 대표 경로로 검증할 수 있다. 실패했을 때 어느 계층을 봐야 하는지 알 수 있는 구성이 목표다.

## 브라우저 테스트와 실제 기기 통화는 다른 증거다

Flutter에는 화면 배치와 상태 표시를 확인하는 테스트가 있다. 좁은 화면에서 버튼이 겹치지 않는지, 경고 문구가 보이는지 같은 UI 요구를 검증할 수 있다. 하지만 테스트 렌더링이 실제 브라우저의 마이크 권한 창이나 오디오 재생 정책까지 대신하지는 않는다.

브라우저 검증은 실제 주소를 열고 로그인 복귀, 새로고침, 스트림 수신과 화면 이동을 보는 단계다. 이때도 테스트 계정과 가짜 미디어 장치를 사용했다면 그 조건을 기록해야 한다. 실제 휴대전화의 출력 경로나 무선망 연결을 확인한 것과 구분할 수 있어야 한다.

실기기에서는 앱을 백그라운드로 보냈다가 돌아오기, 권한 거절 후 변경, 블루투스 장치 전환 같은 조건이 추가된다. 네트워크를 바꿨을 때 양쪽 통화가 복구되는지와 마이크가 남지 않는지도 확인할 대상이다. 기능 테스트 몇 개의 성공률로 이 결과를 대신할 수는 없다.

E2E라는 이름을 사용할 때는 시작과 끝을 밝혀 두는 편이 좋다. HTTP 요청부터 데이터베이스까지인지, 두 클라이언트의 실제 음성 교환까지인지가 다르기 때문이다. 컨테이너 데이터베이스를 붙인 저장소 테스트를 전체 사용자 경험의 E2E라고 부르지 않았다.

캡처 역시 결과의 일부다. 한 장의 화면은 그 순간의 배치가 보였다는 증거이고, 버튼을 눌러 서버 상태가 바뀌었다는 증거는 아닐 수 있다. 전후 화면과 실제 응답, 다시 진입했을 때의 상태를 연결해야 기능 완료를 말할 수 있다.

## 측정값은 조건을 붙여 남긴다

단위 테스트가 빨라졌다는 것과 서비스 요청이 빨라졌다는 것도 다르다. 테스트 대역의 대기 시간을 줄이거나 캐시된 의존성을 사용하면 테스트 실행 시간은 달라진다. 서비스 성능을 말하려면 실제 요청과 데이터, 동시성, 측정 구간을 따로 정의해야 한다.

이번 선택 실행은 관련 규칙의 회귀 여부를 확인하려는 목적이었다. 테스트 수를 사용자 규모나 운영 안정성으로 환산하지 않았다. 통과한 항목과 건너뛴 항목을 나누어 기록하면 다음에 부족한 증거를 채우기 쉬워진다.

성능 실험을 추가한다면 준비 단계와 측정 단계를 나누고 같은 입력을 반복한다. 캐시가 비어 있을 때와 채워진 뒤, 작은 데이터와 큰 데이터에서 결과를 각각 남긴다. 평균만 적으면 일부 요청이 오래 걸리는 현상을 숨길 수 있어 분포도 함께 보는 편이 낫다.

시간 기준이 있는 테스트는 시스템 시계를 직접 기다리기보다 제어 가능한 시계나 스케줄러를 주입하는 방안을 검토할 수 있다. 만료 직전과 직후를 명확히 만들면 실행 환경의 흔들림을 줄일 수 있다. 다만 실제 스케줄러가 연결된 통합 경로까지 전부 가짜로 바꾸지는 않아야 한다.

성공 횟수만큼 실패한 조건도 남긴다. 특정 환경에서만 재현된 실패를 무작정 재실행해 초록색으로 만드는 대신, 경쟁 순서나 외부 의존성 차이를 기록한다. 불안정한 테스트를 삭제할지 고칠지 판단하려면 먼저 무엇을 보호하려 했는지 설명할 수 있어야 한다.

## 바뀐 코드와 함께 오래 갈 테스트

좋은 테스트는 구현을 못 바꾸게 하는 것이 아니라 중요한 동작을 바꿀 때 알려 준다. 반환 데이터와 권한 경계, 중복 부작용을 기준으로 잡으면 내부 메서드가 나뉘어도 요구는 유지된다. 반대로 모든 private 호출 순서를 고정하면 설계 개선이 테스트 수선으로만 보일 수 있다.

공통 준비 코드는 반복을 줄이지만 중요한 조건까지 숨기지 않아야 한다. 어떤 사용자가 어느 세션에 참여했고 어떤 저장 상태에서 시작하는지 테스트 본문에서 읽을 수 있어야 실패 원인을 이해하기 쉽다. 많은 기본값으로 만든 만능 fixture는 권한과 상태의 차이를 감출 수 있다.

테스트 데이터에는 실제 사용자 토큰이나 메일 주소, 내부 접속 정보를 쓰지 않는다. 통합 테스트가 임시 자격 증명을 만들더라도 운영 비밀값과 섞이지 않도록 분리한다. 실패 보고서와 캡처가 공유될 수 있다는 점까지 고려해 공개 가능한 자료를 사용한다.

정리 단계도 테스트의 일부다. 열린 연결과 실행기, 임시 컨테이너가 남으면 다음 테스트가 실패하거나 환경 자원을 계속 사용한다. 한 번 성공한 결과보다 반복 실행에서 같은 시작 상태를 만들 수 있는지가 자동화의 신뢰를 높인다.

이번 실행 기록에서 다음으로 채울 칸은 PostgreSQL 잠금 테스트의 실제 수행 결과다. 그 항목이 빠져 있다는 사실을 숨기지 않으니 무엇을 더 확인해야 하는지도 선명해졌다. 테스트가 통과했냐는 질문에 이제는 어떤 경계가 통과했고 무엇은 아직 실행하지 않았는지 함께 답하려 한다.
