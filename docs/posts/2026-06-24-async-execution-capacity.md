오래 걸리는 작업을 다른 스레드로 보내면 요청을 빨리 돌려줄 수 있다. 그렇다고 그 작업이 사라지는 것은 아니다. 다음 질문은 어디에 쌓이고, 얼마나 기다리며, 끝내 실패하면 누가 알아차리는가다.

기존 글은 Async 어노테이션으로 응답 시간을 크게 줄였다고 적었지만 이를 입증할 측정 자료는 없었다. 현재 VoiceLink 서버 코드를 검색해도 그 어노테이션을 도입한 경로 대신 명시적인 실행기를 쓰는 [Outbox 작업자](https://so-dak.com/%eb%b6%84%ec%82%b0-%ec%8b%9c%ec%8a%a4%ed%85%9c-%ec%a0%95%ed%95%a9%ec%84%b1-%eb%b3%b4%ec%9e%a5-transactional-outbox-pattern%ec%9c%bc%eb%a1%9c-%eb%a7%a4%ec%b9%ad-%ec%9d%b4%eb%b2%a4%ed%8a%b8-%eb%b0%9c/)가 확인되었다. 실제 구현과 도입 검토를 나눠 설명하기로 했다.

아래는 Java 17의 제한된 스레드 풀 실험과 Spring Boot 3.2.5 프로젝트의 작업자 코드를 바탕으로 정리한 내용이다. 수만 명의 트래픽을 처리했다거나 운영 응답 시간을 줄였다는 주장은 하지 않았다. 작은 실험은 포화 조건을 이해하기 위한 것이며 서비스 부하 시험을 대신하지 않는다.

## 접수와 완료를 같은 성공으로 부르지 않기

동기 요청은 호출자가 결과를 기다리는 동안 실패도 직접 전달받기 쉽다. 비동기 작업을 접수한 뒤 응답하면 그 이후의 실패는 이미 끝난 HTTP 응답으로 돌려줄 수 없다. 사용자에게 접수됨을 알리는지 실제 완료를 알리는지부터 API의 의미를 정해야 한다.

작업 상태를 조회하는 기능이 필요하다면 식별자와 진행 상태, 완료 결과를 저장할 위치가 필요하다. 단지 메모리 실행기에 Runnable을 넣고 성공 응답을 주면 서버가 재시작될 때 아직 실행하지 않은 작업을 잃을 수 있다. 스레드 풀은 영속적인 작업 저장소가 아니다.

반대로 결과가 반드시 현재 요청에 필요하다면 다른 스레드에 넘긴 뒤 바로 기다리는 것만으로 응답 시간이 짧아지지 않는다. 호출 스레드와 작업 스레드를 동시에 점유할 수도 있다. 병렬로 수행할 독립 작업이 있는지와 기다리는 전체 시간을 나누어 살펴야 한다.

외부 API가 느릴 때 전용 풀로 분리하면 다른 작업의 실행 자원을 보호하는 데 도움이 될 수 있다. 하지만 CPU와 메모리, 데이터베이스 연결, 외부 요청 한도는 여전히 공유될 수 있다. 스레드 풀을 나눴다고 다른 요청에 영향이 전혀 없어진다는 표현은 과장이다.

업무 중요도에 따라 접수 방식도 달라진다. 사라져도 다시 만들 수 있는 임시 갱신과 반드시 남겨야 하는 발송은 같은 메모리 큐에 넣을 이유가 없다. 후자는 데이터베이스에 작업을 남기는 Outbox처럼 재시작 뒤 복구할 근거를 함께 고려할 수 있다.

## 큐가 차야 최대 작업자가 늘어나는 경우

ThreadPoolExecutor의 일반적인 구성에서는 기본 작업자를 사용한 뒤 큐에 넣고, 큐가 더 받지 못할 때 최대 작업자까지 확장한다. 최대 크기를 크게 정해도 큐가 넓으면 그 크기를 바로 사용하지 않을 수 있다. 설정 숫자를 읽는 순서가 실제 동작과 맞아야 한다.

무제한 큐를 두면 접수 거절은 늦춰지지만 대기 시간이 길어지고 메모리에 작업이 쌓일 수 있다. 작업 하나가 요청 본문이나 큰 객체를 잡고 있으면 큐 길이에 비례해 부담도 커진다. 큐를 무한히 늘리는 것은 처리 능력을 늘리는 것과 다르다.

짧은 실험에서는 작업이 끝나지 않도록 문을 닫아 두고 접수만 늘려 봤다. 기본 작업자 두 개, 최대 네 개, 큐 여덟 칸이라는 설명용 값이다. 실제 서비스에 그대로 적용할 권장값이 아니라 실행과 대기의 상한을 확인하려고 작게 정했다.

```java
import java.util.concurrent.*;

public class AsyncCapacityDemo {
    public static void main(String[] args) throws Exception {
        var gate = new CountDownLatch(1);
        var pool = new ThreadPoolExecutor(
            2, 4, 30, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(8),
            new ThreadPoolExecutor.AbortPolicy());
        int accepted = 0;
        int rejected = 0;
        try {
            for (int i = 0; i < 13; i++) {
                try {
                    pool.execute(() -> {
                        try {
                            gate.await();
                        } catch (InterruptedException e) {
                            Thread.currentThread().interrupt();
                        }
                    });
                    accepted++;
                } catch (RejectedExecutionException e) {
                    rejected++;
                }
            }
            System.out.println("accepted=" + accepted + ", rejected=" + rejected);
        } finally {
            gate.countDown();
            pool.shutdown();
            if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
                pool.shutdownNow();
                throw new IllegalStateException("Worker shutdown timed out");
            }
        }
    }
}
```

작업자가 끝나지 않으므로 앞의 작업이 빠져나가 접수 공간을 만드는 상황을 제외했다. 실행 가능한 네 작업과 대기 가능한 여덟 작업을 넘어선 요청은 거절된다. 실험에서 확인하려는 것은 처리 속도가 아니라 제한에 도달했을 때 접수 경로가 실패를 드러내는지다.

이 코드를 독립된 Java 프로그램으로 실행한 출력은 접수 열두 건, 거절 한 건이었다. 작업을 붙잡아 둔 조건에서 한 번 수행한 기능 실험이며, 처리 시간이나 실제 서버의 최대 요청 수를 측정한 결과는 아니다. 대기 문을 연 뒤에는 작업자가 정리되고 프로그램이 종료되는 것까지 확인했다.

거절 정책이 예외를 내면 호출부가 이를 업무 결과로 처리해야 한다. 임시 과부하 응답을 줄지, 영속 작업 저장소에 남긴 뒤 나중에 처리할지는 서비스 요구에 달려 있다. 모든 예외를 잡고 성공으로 응답하면 접수하지 못한 작업이 조용히 사라질 수 있다.

호출 스레드가 대신 실행하는 정책을 선택하면 작업을 버리지 않는 대신 호출자가 오래 기다릴 수 있다. 웹 요청 스레드에서 실행한다면 비동기로 분리하려던 지연이 다시 요청 경로로 돌아온다. 이름만 보고 안전한 정책이라고 고르기보다 포화 때 어떤 자원이 느려지는지 확인해야 한다.

## 실제 Outbox 작업자는 다른 상한을 갖고 있었다

VoiceLink의 발행 작업자는 고정 크기 실행기에 선점한 작업을 제출하고 각 Future의 완료를 기다린다. 생성 설정의 기본 작업자 수는 여덟 개이고, 한 번에 선점할 작업에도 기본 배치 크기가 있다. 일반 요청마다 작업을 무제한 제출하는 예제와 같은 조건은 아니다.

그렇다고 고정 크기 풀 자체가 제한된 대기열이라는 뜻은 아니다. 사용한 생성 메서드가 제공하는 큐 특성과 호출부가 제출하는 배치의 상한을 나눠 봐야 한다. 현재 호출 경로의 제한이 유지되는지 확인하지 않고 풀 이름만으로 메모리 사용량을 보장할 수는 없다.

발행 한 건에는 Redis 저장과 실시간 메시지 전달, 데이터베이스 상태 갱신이 포함된다. 작업자 수를 늘리면 이 외부 자원에 동시에 접근하는 수도 늘어난다. 데이터베이스 연결 풀이 먼저 포화되면 스레드가 많아져도 실제 진행하는 작업은 제한될 수 있다.

메시지 발행은 확인 응답을 기다리는 제한 시간이 있지만, 작업 Future를 기다리는 구간은 별도 구조다. 하나의 외부 호출에 제한 시간이 있다는 이유로 작업 전체가 같은 시간 안에 끝난다고 말할 수 없다. 각 저장소 호출과 완료 기록까지 포함해 기다리는 구간을 찾아야 한다.

현재 구조는 작업이 선점된 상태를 데이터베이스에 남기고, 임대가 만료되면 다시 선점할 수 있도록 한다. 프로세스 안의 Future만으로 복구를 결정하는 구조와 다르다. 작업 실행과 작업 소유권을 분리해서 읽으면 스레드 풀이 담당하지 않는 부분이 드러난다.

작업이 오래 걸려 임대를 넘었을 때는 늦은 작업자가 새 소유자의 완료 상태를 덮지 않아야 한다. 이런 조건은 실행기의 동시성 제어만으로 해결되지 않는다. 저장소의 소유권 확인과 외부 부작용의 중복 처리까지 함께 설계해야 한다.

## Async를 붙인다면 호출 경로부터 확인한다

Spring의 기본 프록시 방식에서 비동기 어노테이션은 프록시를 통과하는 호출에 적용된다. 같은 객체 안에서 메서드를 직접 호출하면 기대한 비동기 경로가 되지 않을 수 있다. 어노테이션이 붙은 메서드가 존재한다는 사실과 실제 호출이 다른 스레드에서 실행된다는 사실은 구분해야 한다.

실행기를 여러 개 쓴다면 어느 풀을 사용할지도 명시하는 편이 읽기 쉽다. 외부 알림과 CPU 연산을 같은 큐에 넣으면 한 종류의 느린 작업이 다른 종류의 대기를 늘릴 수 있다. 그렇다고 기능마다 풀을 만들면 스레드 총량이 커지므로 자원 예산 안에서 나눠야 한다.

반환형이 Future라면 호출자가 실패를 관찰할 수 있는 경로를 정해야 한다. 아무도 결과를 기다리거나 완료 콜백을 처리하지 않으면 실패가 묻힐 수 있다. 반환값이 없는 비동기 메서드는 예외 처리기를 통해 어디에 기록하고 어떻게 복구할지 따로 설계해야 한다.

요청 스레드의 트랜잭션이 작업 스레드에 그대로 이어진다고 가정해서도 안 된다. 아직 커밋하지 않은 행을 비동기 작업이 읽으려 하면 기대와 다른 상태를 볼 수 있다. 필요한 데이터가 언제 확정되는지와 작업 자체의 트랜잭션 범위를 명시해야 한다.

커밋 이후 실행하도록 예약해도 프로세스가 그 사이 종료되면 작업이 사라질 수 있다. 커밋 후 호출과 영속적인 전달 보장은 같은 기능이 아니다. 반드시 수행해야 하는 작업이라면 데이터 변경과 실행할 작업 기록을 함께 저장하는 방식을 검토하는 이유다.

요청 추적 정보나 사용자 정보도 자동으로 안전하게 옮겨진다고 보지 않는다. 필요한 최소 정보만 명시적으로 전달하고, 재사용되는 작업 스레드에 이전 요청의 정보가 남지 않도록 정리해야 한다. 토큰 원문이나 큰 요청 객체를 그대로 잡아 두는 방식은 피하는 편이 낫다.

## 제한 시간 뒤의 작업도 생각해야 한다

Future를 기다리다 제한 시간이 지나면 호출자는 기다리기를 끝낼 수 있다. 그러나 외부 요청이나 계산이 실제로 중단되었는지는 다른 문제다. 취소 요청이 전달되더라도 실행 코드와 라이브러리가 중단에 협조해야 자원이 정리된다.

같은 작업을 다시 시도할 때 이전 요청이 늦게 성공하면 부작용이 두 번 생길 수 있다. 발송이나 등록처럼 중복이 중요한 동작은 업무 식별자를 기준으로 같은 작업임을 구분해야 한다. 제한 시간은 실패가 확정되었다는 신호가 아니라 결과를 아직 모를 수 있다는 신호이기도 하다.

대기열에서 이미 오래 기다린 작업도 따로 본다. 실행을 시작한 뒤의 제한 시간만 두면 사용자에게는 허용 시간을 훨씬 넘길 수 있다. 접수 시각과 실행 시작 시각, 완료 시각을 나눠 기록하면 대기가 긴 것인지 실행이 느린 것인지 구분할 수 있다.

작업 기한이 지난 뒤에도 실행할 가치가 있는지 판단하는 정책도 필요하다. 최신 상태만 의미 있는 갱신은 오래된 작업을 버리거나 합칠 수 있고, 반드시 처리할 기록은 나중에도 이어가야 한다. 모든 작업을 같은 FIFO 큐에 넣는 것보다 요구에 맞는 선택이다.

재시도에는 횟수와 간격뿐 아니라 최종 실패 상태가 있어야 한다. 계속 실패하는 작업을 무한히 다시 넣으면 정상 작업의 대기까지 늘어난다. 사람이 확인할 실패 기록과 안전한 재처리 방법을 남기는 것이 단순 로그 출력보다 복구에 도움이 된다.

## 종료할 때 무엇을 남길지 정한다

애플리케이션 종료 시 새 접수를 막고 진행 중 작업이 끝나기를 기다릴지 결정해야 한다. 즉시 종료 요청을 보낸다고 모든 외부 I/O가 취소되는 것은 아니다. 배포 과정의 종료 유예와 각 작업의 최대 대기 시간을 맞춰야 한다.

메모리 큐에 남은 작업을 잃어도 되는지와 영속 저장소에서 다시 읽을 수 있는지는 여기서 큰 차이를 만든다. 복구 가능한 작업은 소유권 만료 뒤 다시 선점할 수 있지만, 중간에 외부로 보낸 요청의 중복은 별도 고려해야 한다. 종료와 재시도는 같은 상태 모델 안에서 다뤄야 한다.

실험 코드는 대기 문을 열고 종료를 기다린 뒤 제한을 넘으면 강제 중단을 요청한다. 이 정리가 빠지면 예제를 실행한 프로세스가 끝나지 않거나 다음 실험에 영향을 줄 수 있다. 작은 코드에서도 누가 실행기를 닫는지 드러내려는 이유다.

운영 검증에서는 큐 길이뿐 아니라 가장 오래 기다린 작업의 나이와 거절 횟수를 본다. 큐가 짧아도 단일 작업이 오래 막혀 있을 수 있고, 평균 처리 시간이 좋아도 일부 요청이 계속 밀릴 수 있다. 처리량 숫자 하나보다 포화로 가는 신호를 먼저 관찰하는 편이 낫다.

작업자 수를 바꿔 비교할 때는 입력량과 외부 의존성 조건을 고정한다. 같은 시간에 외부 서버가 빨라졌다면 풀 설정의 효과로 돌릴 수 없다. CPU 작업과 I/O 대기 작업을 나눠 측정하고 데이터베이스 연결 대기도 함께 기록해야 변경 이유가 남는다.

이제 비동기 설명의 마지막 문장은 “응답이 빨라졌다”로 끝나지 않는다. 접수하지 못했을 때 무엇을 돌려주고, 시작한 작업이 끝나지 않으면 어디서 다시 찾는지가 함께 있어야 한다. 그 답을 정한 뒤에야 풀 크기의 숫자를 비교할 수 있다.
