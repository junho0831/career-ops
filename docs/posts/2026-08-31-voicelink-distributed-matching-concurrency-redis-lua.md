대기열에서 가장 오래 기다린 사람을 읽고 지우면 매칭이 끝날 것처럼 보인다. 그런데 읽기와 삭제 사이에 다른 요청이 들어오면, 두 요청이 같은 상대를 골라도 이상하지 않다. 문제는 정렬 방법보다 후보를 가져갔다는 사실을 어느 순간 확정하느냐에 있었다.

VoiceLink의 `find_opponent.lua`와 `RedisMatchingStore`, `MatchFinalizer`를 함께 읽었다. Java 17과 Spring Boot 3.2.5를 쓰는 현재 소스 기준이며, 운영 트래픽을 재현한 성능 보고서는 아니다. 앞선 글의 ‘이중 매칭 0건’은 측정 환경과 표본을 제시하지 못해 제목과 본문에서 뺐다. 여기서는 구현이 막는 경합과 아직 별도 검증이 필요한 경계를 나눠 보려고 한다.

## 두 명이 같은 후보를 읽는 순간

대기자 B가 있고, 서로 다른 서버의 A와 C가 거의 동시에 후보를 조회한다고 가정해 보자. 조회만으로 B를 예약하지는 않는다. A가 B를 읽은 뒤 삭제하기 전에 C도 같은 값을 읽을 수 있고, 두 서버가 읽은 결과만 믿고 방을 만들면 중복 배정으로 이어진다.

삭제 결과를 확인하는 것부터 차이가 생긴다. `ZREM`이 하나를 제거했다는 응답을 준 요청만 선점에 성공했다고 처리해야 한다. 이미 다른 요청이 지운 후보를 반환해서는 안 된다. 다만 조회, 유효성 확인, 삭제가 여러 왕복으로 흩어져 있으면 그 사이에 바뀌는 상태까지 따져야 하므로, 현재 구현은 이 과정을 짧은 스크립트 안에 모았다.

Redis가 명령을 처리하는 순서와 애플리케이션이 여러 명령을 조합하는 순서는 같은 보장이 아니다. 각각의 조회와 삭제가 정상 실행되어도 두 요청의 명령이 사이에 끼어들 수 있다. 그래서 ‘Redis를 쓰니까 안전하다’는 설명만으로는 부족하다. 다른 요청이 끼어들면 안 되는 연산 묶음부터 정하는 편이 정확하다.

애플리케이션 객체에 락을 걸면 같은 프로세스의 요청은 막을 수 있다. 하지만 다른 서버의 객체까지 잠그지는 못한다. 이 글에서 Lua를 선택한 이유는 모든 매칭 작업을 Redis로 옮기기 위해서가 아니라, 여러 서버가 공유하는 대기열의 작은 선점 구간을 같은 곳에서 판단하기 위해서다.

## 정렬된 대기열과 살아 있는 대기는 다르다

현재 대기열은 사용자 식별자를 ZSET의 member로, 등록 시각을 score로 보관한다. 이 정보만 보면 누가 먼저 들어왔는지는 알 수 있다. 반면 그 사용자가 화면을 닫았는지, 네트워크가 끊겼는지까지는 알 수 없다. 오래된 항목이 남았다는 사실과 아직 연결 가능한 사람이라는 판단을 분리해야 했다.

이를 위해 별도의 presence 키에 유효기간을 둔다. 대기 갱신 시 처음 만들어진 키라면 ZSET에도 등록하고, 이미 존재하면 만료 시간만 연장한다. 매번 score를 현재 시각으로 바꾸지 않으므로 정상적으로 기다리는 사람을 갱신할 때마다 줄의 맨 뒤로 보내지는 않는다. 이 동작은 저장소 단위 테스트에서도 등록과 갱신 두 경우로 나뉘어 있다.

TTL은 연결 상태를 즉시 알려 주는 센서가 아니다. 클라이언트가 끊겨도 키가 남은 시간 동안에는 살아 있다고 판단할 수 있고, 일시적인 갱신 지연 때문에 실제로는 연결된 사람이 만료될 수도 있다. 현재 기본 대기 타임아웃은 25초이며 presence에는 10초를 더한다. 35초라는 값은 코드의 기본 정책이지 모든 망에서 적절하다고 검증된 상수는 아니다.

설정을 바꿀 때는 매칭 대기 시간만 보고 결정할 수 없다. 재구독 간격, 서버 정지 시간, 네트워크 지연을 같이 봐야 한다. TTL을 짧게 잡으면 잔류 대기가 빨리 없어지는 대신 정상 사용자를 제외할 가능성이 커진다. 길게 잡으면 그 반대다. 대기열 길이와 실제 연결 수를 따로 관찰해야 이 차이를 설명할 수 있다.

## 스크립트가 책임지는 범위

현재 스크립트는 앞쪽 후보를 일정 개수만 읽고, 자신을 제외한 후보를 하나씩 제거해 본다. 제거에 성공한 후보에게 presence가 남아 있으면 해당 키도 지우고 식별자를 반환한다. presence가 없다면 대기열에 남은 오래된 항목으로 보고 다음 후보를 살핀다.

아래는 저장소 코드에서 분기만 남긴 발췌다. 실제 실행 파일에는 후보 범위와 입력값을 다루는 앞부분이 더 있다. 독립적인 배포 예제로 복사하기보다, 어느 조건에서 후보가 반환되는지 확인하는 용도다.

```lua
for _, candidateId in ipairs(candidates) do
    if candidateId ~= currentUserId then
        local removed = redis.call('ZREM', waitingZsetKey, candidateId)
        if removed == 1 then
            local presenceKey = presencePrefix .. candidateId
            if redis.call('EXISTS', presenceKey) == 1 then
                redis.call('DEL', presenceKey)
                return candidateId
            end
        end
    end
end
return nil
```

핵심은 반환값의 의미다. 식별자가 왔다는 것은 이 스크립트가 후보를 대기열에서 선점했다는 뜻이다. 통화방이 저장되었다거나 상대의 화면에 연결 정보가 도착했다는 뜻은 아니다. 이 의미를 넓혀 해석하면 이후 데이터베이스 [저장 실패](https://so-dak.com/%eb%b6%84%ec%82%b0-%ec%8b%9c%ec%8a%a4%ed%85%9c-%ec%a0%95%ed%95%a9%ec%84%b1-%eb%b3%b4%ec%9e%a5-transactional-outbox-pattern%ec%9c%bc%eb%a1%9c-%eb%a7%a4%ec%b9%ad-%ec%9d%b4%eb%b2%a4%ed%8a%b8-%eb%b0%9c/)까지 Lua가 처리한다고 착각하기 쉽다.

Redis는 스크립트 실행 중 다른 명령이 끼어드는 것을 막는다. 대신 실행이 길어지면 다른 요청도 기다려야 한다. 그래서 전체 대기열을 끝없이 훑는 식으로 만들지 않았다. 앞쪽 후보를 제한해서 읽는 정책은 한 번의 점유 시간을 제한하지만, 그 범위 밖에 유효한 후보가 있어도 이번 호출은 못 찾을 수 있다는 비용이 있다.

이때 빈 반환값을 ‘서비스 전체에 대기자가 없다’고 해석하면 안 된다. 살펴본 범위에서 상대를 반환하지 못했다는 의미에 가깝다. 현재 Java 호출부는 스크립트 실행 예외도 로그를 남긴 뒤 빈 결과로 바꾼다. 사용자에게 대기 상태를 돌려줄 수는 있어도, 운영 지표에서는 정상 대기와 Redis 장애를 구분하지 않으면 문제를 늦게 발견하게 된다.

## 후보를 얻은 다음에도 취소는 들어온다

후보를 선점한 직후 사용자가 취소 버튼을 누를 수 있다. Redis에서 후보를 제거하는 순간과 데이터베이스에 통화 세션을 쓰는 순간을 하나의 트랜잭션으로 묶어 둔 구조가 아니므로, 선점 이후의 경합을 별도로 처리해야 한다.

`MatchFinalizer`는 세션 생성 전, 생성 후, 응답 생성 후에 취소 마커를 다시 확인한다. 취소한 쪽에는 대기 응답으로 요청을 마무리하고, 취소하지 않은 상대는 다시 대기시킨다. 이미 세션을 만들었다면 조용히 종료시키는 분기도 있다. 반복 확인이 보기에는 중복처럼 보이지만, 각각 그 사이에 진행된 작업을 되돌리기 위한 위치다.

이 구조를 설명하면서 ‘취소 경합을 완전히 제거했다’고 끝내기는 어렵다. 마지막 확인 뒤에도 시간은 흐른다. 취소 신호가 언제 기록되고 어떤 소비자가 언제 읽는지, 이미 전송된 결과를 클라이언트가 어떻게 처리하는지까지 봐야 한다. 확인 지점을 늘린 사실은 근거가 되지만, 가능한 모든 실행 순서를 검증했다는 근거가 되지는 않는다.

예외 처리도 중요한 부분이다. 세션 저장이나 응답 생성에 실패하면 현재 트랜잭션을 롤백 대상으로 표시하고, 취소하지 않은 사용자를 다시 대기시키는 보상 경로가 있다. Redis에서 이미 제거한 후보가 데이터베이스 롤백만으로 자동 복원되는 것은 아니기 때문이다. 이 분기를 빼고 성공 코드만 보여 주면 대기자가 어디에서 사라지는지 설명할 수 없다.

보상 작업 자체도 실패할 수 있다. Redis가 계속 응답하지 않거나 프로세스가 그 전에 종료되면 재큐잉 호출까지 도달하지 못할 수 있다. presence 만료와 클라이언트 재구독이 어느 범위까지 회복을 도와주는지 따로 검증할 필요가 있다. 요청 실패를 무조건 즉시 재시도하면 같은 장애 지점으로 부하가 다시 몰릴 수 있어 횟수와 대기 정책도 함께 다뤄야 한다.

## 원자성과 복구 가능성을 따로 시험하기

저장소의 `RedisMatchingStoreTest`는 Mockito로 명령 호출, TTL 갱신, 반환값 변환을 확인한다. 예를 들어 presence가 처음 생겼을 때만 ZSET에 추가하는지, 취소 마커에 설정한 유효기간을 쓰는지를 읽을 수 있었다. 이런 테스트는 Java 코드가 의도한 요청을 보내는지 확인하는 데 유용하다.

하지만 Redis를 가짜 객체로 바꾼 테스트가 실제 Lua의 동시 실행 특성까지 증명하지는 않는다. 그 부분은 격리한 Redis에 서로 다른 요청자를 동시에 투입하고, 반환된 후보가 중복되지 않는지 확인하는 별도 실험이 필요하다. 자기 자신만 있는 대기열, presence가 만료된 후보, 탐색 범위 앞쪽을 오래된 항목이 채운 상황도 나눠 넣어야 한다.

실험 결과를 남긴다면 총 요청 수 하나보다 성공, 정상 대기, 실행 오류, 중복 후보 반환을 각각 세는 편이 낫다. Redis 버전, 클라이언트 수, 탐색 개수, 요청 간격과 재시도 정책을 기록해야 다른 사람이 같은 조건으로 비교할 수 있다. 아직 실행하지 않은 실험의 예상 결과를 실제 결과 표에 넣지는 않았다.

다음 단계에서는 후보 선점 이후 데이터베이스 쓰기를 일부러 실패시켜 볼 수 있다. 세션이 남지 않는지와 두 사용자가 다시 대기할 수 있는지를 함께 봐야 한다. 하나의 상태만 확인하면 롤백은 됐지만 상대가 대기열에서 사라진 경우를 놓칠 수 있다. 취소 요청과 재큐잉이 겹칠 때 취소 의도가 되살아나지 않는지도 같은 이유로 중요하다.

현재 결과 전달은 DB outbox와 Redis 결과 캐시, RabbitMQ 전달 경로가 이어진다. 후보 선점이 안전해도 결과 전달 실패로 사용자가 대기 화면에 남을 수 있다. 이 단계는 선점 알고리즘의 성공률과 별도로 봐야 한다. 화면까지 도착한 매칭과 저장소에서 반환한 후보 수를 같은 지표로 취급하지 않는 것이 출발점이다.

## 지금 코드에서 남겨 둘 한계

타임아웃된 요청의 정리 콜백도 같은 사용자라는 이유만으로 새 대기를 지우면 안 된다. 매칭 화면을 나갔다가 바로 들어오는 경우에는 예전 요청과 새 요청이 잠깐 공존할 수 있다. 로컬 대기 객체가 정리하려는 요청과 같은 객체인지 확인하는 조건까지 이어서 봐야 한다. 후보 선점 테스트만으로는 발견하기 어려운 생명주기 문제다.

결과를 다시 가져오는 코드도 따로 읽을 필요가 있다. 현재 `claimMatchResult`는 값을 읽고 그다음 삭제하며, 이 두 명령을 하나의 원자 연산으로 묶지는 않는다. 같은 사용자의 요청 두 개가 겹치면 결과를 각각 읽을 가능성을 후보 선점과 분리해서 검토해야 한다. 메서드 이름에 회수라는 뜻이 담겨 있어도 이름이 동시성 보장을 대신하지는 않는다.

재시작 상황도 빠뜨리기 쉽다. 스크립트 캐시는 Redis의 영구 데이터와 같지 않으므로 서버 재시작 뒤에는 다시 적재하는 경로가 필요하다. Spring Data Redis의 스크립트 실행 지원이 캐시 미스를 처리하는 방식까지 확인해야 배포 직후와 평상시의 동작을 같은 조건으로 비교할 수 있다. 장애가 나지 않은 한 번의 호출만으로 복구 동작을 판단하지 않으려는 이유다.

현재 Lua는 presence 접두사와 후보 식별자를 붙여 접근할 키를 만든다. Redis 공식 문서는 스크립트가 접근하는 키를 명시적으로 전달하도록 요구한다. 따라서 이 구현을 그대로 Redis Cluster에 옮겨도 안전하다고 설명할 수 없다. 여러 키가 놓이는 슬롯과 데이터 구조부터 검토해야 하며, 단일 Redis에서의 동작 설명과 클러스터 지원 여부는 별개다.

또한 도착 시각을 score로 쓴다고 엄격한 선착순을 보장하는 것도 아니다. 서버 간 시계 차이, 같은 점수의 정렬, 탐색 제한과 재큐잉이 순서에 영향을 준다. 공정성이 중요한 서비스라면 평균 대기 시간 외에 오래 기다린 사용자의 분포와 반복 제외되는 조건을 봐야 한다. 빠르게 후보를 꺼내는 것과 누구도 오래 기다리지 않는 것은 다른 목표다.

코드를 따라가고 나니 이 기능을 ‘Lua로 이중 매칭 해결’이라는 한 문장으로 설명하기 어려워졌다. Lua가 담당하는 작은 선점 구간을 명확히 하고, 그 밖의 취소와 저장 실패를 따로 다루는 편이 실제 구현에 가깝다. 다음에 먼저 확인할 것은 처리량 숫자가 아니라, 후보를 꺼낸 뒤 실패했을 때 두 사용자가 어디에 남는지다.
