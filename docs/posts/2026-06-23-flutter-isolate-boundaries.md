JSON 파싱 함수를 Future로 감싸면 화면이 덜 멈출까. 호출 형태만 비동기로 바뀌고 같은 실행 공간에서 긴 계산이 계속되면 기대한 효과가 나지 않을 수 있다. 기다리는 작업과 CPU를 사용하는 작업을 먼저 나눠 봐야 한다.

기존 글은 Isolate를 적용해 프레임 저하를 없앴다는 식으로 설명했지만 이를 뒷받침할 측정 기록은 없었다. 현재 VoiceLink의 Flutter 소스에서도 compute나 Isolate를 적용한 경로를 확인하지 못했다. 도입 경험 대신 어떤 조건에서 연산 분리가 필요한지 검토하는 글로 범위를 바꿨다.

프로젝트의 웹 빌드는 Flutter 3.38.3을 사용한다. 아래 내용은 현재 공식 API 설명과 실제 클라이언트의 비동기 상태 처리 구조를 대조한 설계 검토이며, 휴대전화에서 프레임 시간을 비교한 결과는 아니다. 웹과 네이티브의 동작 차이를 특히 분리했다.

## await가 계산을 다른 곳으로 보내 주지는 않는다

네트워크 응답을 기다리는 동안 실행 공간을 비우는 일과 이미 받은 데이터를 오래 계산하는 일은 다르다. 비동기 I/O를 기다리는 구간은 다른 이벤트가 진행할 여지가 있지만, 큰 반복문이 같은 isolate를 점유하면 화면 관련 작업도 기다릴 수 있다.

함수 앞에 async를 붙였다고 그 안의 모든 코드가 별도 스레드로 이동하지 않는다. JSON 해석과 정렬, 객체 변환이 어디서 실행되는지를 봐야 한다. Future를 반환한다는 인터페이스만으로 CPU 연산의 위치를 판단하지 않는 것이 첫 번째 기준이다.

Flutter 전체가 단일 스레드로만 구성되어 있다는 표현도 피했다. 여기서 문제로 삼는 것은 주 isolate에서 수행하는 Dart 코드가 화면 갱신과 같은 이벤트 처리 시간을 오래 차지하는 상황이다. 엔진의 다른 작업까지 한 문장으로 같은 실행 공간이라고 묶으면 원인을 흐린다.

화면 끊김의 원인이 늘 파싱인 것도 아니다. 큰 위젯 트리 재구성이나 레이아웃, 이미지 처리와 그리기 비용이 원인일 수 있다. 계산을 옮기기 전에 어떤 구간이 긴지 관찰해야 불필요한 동시성 코드부터 추가하지 않을 수 있다.

기준 프레임 시간도 기기의 주사율에 따라 달라진다. 60Hz의 한 주기는 약 16.7밀리초이고 120Hz에서는 약 8.3밀리초다. 이는 시간 예산을 이해하기 위한 산술값이며 어떤 앱이 그 시간을 지켰다는 측정 결과는 아니다.

## 옮길 것은 UI가 아니라 독립적인 변환

Isolate로 나누기 쉬운 작업은 입력과 출력이 분명한 순수한 변환이다. 예를 들어 받은 문자열을 검사하고 필요한 데이터 구조로 바꾸는 연산은 화면 객체를 직접 알 필요가 없다. 입력이 같을 때 같은 결과를 만드는 함수로 분리하면 기능 테스트도 쉬워진다.

반면 BuildContext나 위젯 상태, 화면에서 쓰는 변경 가능한 저장소를 통째로 전달하려 하면 경계가 흐려진다. isolate 사이에는 각자 메모리와 전달 가능한 값의 제약이 있다. 다른 실행 공간에서 화면 상태를 직접 바꾸는 구조로 이해해서는 안 된다.

데이터 변환에는 형식 오류 처리도 포함해야 한다. 파싱 성공만 가정한 예제는 실제 응답이 바뀌거나 필수 값이 빠졌을 때 어디서 실패하는지 설명하지 못한다. 아래는 필요한 숫자 필드만 읽는 설명용 함수이며, 전체 앱에 적용하거나 기기에서 실행한 코드는 아니다.

```dart
import 'dart:convert';
import 'package:flutter/foundation.dart';

List<int> parseItemIds(String source) {
  final decoded = jsonDecode(source);
  if (decoded is! List) {
    throw const FormatException('Expected a list');
  }
  return decoded.map((item) {
    if (item is! Map || item['id'] is! int) {
      throw const FormatException('Expected an integer id');
    }
    return item['id'] as int;
  }).toList(growable: false);
}

Future<List<int>> parseItemIdsAsync(String source) {
  return compute(parseItemIds, source, debugLabel: 'parse-item-ids');
}
```

이 예제는 네트워크 요청과 화면 변경을 함수 밖에 둔다. 실패는 Future를 기다리는 호출부에서 처리해야 하며, 오류가 났을 때 빈 목록으로 바꿀지 사용자에게 재시도를 안내할지는 업무 규칙이다. 잘못된 응답을 조용히 정상적인 빈 결과로 만드는 선택은 신중해야 한다.

입력 크기도 따로 제한할 필요가 있다. 큰 문자열을 다른 곳에서 파싱한다고 앱 전체 메모리가 무한해지는 것은 아니다. 서버 페이지 크기를 줄이거나 필요한 필드만 받는 방법으로 계산량 자체를 줄일 수 있는지 먼저 비교할 만하다.

최상위 함수를 사용한 것은 전달할 의존성을 분명하게 하려는 선택이다. 모든 콜백이 반드시 최상위 함수여야 한다고 일반화하지 않았다. 클로저가 의도하지 않은 객체까지 붙잡을 수 있으므로, isolate로 보낼 값과 캡처한 범위를 작게 유지하는 편이 검토하기 쉽다.

## 웹의 compute는 같은 병렬 효과를 보장하지 않는다

공식 Flutter API 설명에서 compute는 네이티브 플랫폼과 웹의 실행 방식이 다르다. 웹에서는 현재 이벤트 루프에서 콜백을 실행한다. 같은 함수 이름을 썼다고 웹에서도 별도 isolate가 CPU 연산을 병렬로 처리한다고 기대하면 안 된다.

이 차이는 웹과 모바일을 함께 제공하는 프로젝트에서 중요하다. 휴대전화 네이티브 앱에서 도움이 된 변환이 브라우저에서는 같은 효과를 보이지 않을 수 있다. 플랫폼을 구분하지 않고 적용 후 60FPS를 달성했다는 제목을 붙일 근거가 부족했던 이유다.

웹에서 긴 작업이 문제라면 먼저 입력을 줄이거나 계산을 나누는 방식을 검토할 수 있다. 작업을 작은 단위로 나누고 이벤트 루프에 기회를 주는 방식은 총 계산량을 줄이지는 않지만 긴 독점을 줄이는 데 목적이 있다. 상태 중간 결과를 어떻게 처리할지 새로 정해야 한다.

별도의 Web Worker를 사용하는 접근은 다른 구현 경계다. 데이터 전달과 빌드, 오류 처리, 브라우저 호환성을 검토해야 하며 compute를 한 줄 바꾸는 것과 같은 도입이라고 설명할 수 없다. 실제로 필요한 계산이 웹에서 반복되는지부터 측정할 일이다.

플랫폼 분기를 넣을 때 기능 결과는 같아야 한다. 네이티브에서는 엄격하게 형식을 검사하고 웹에서는 오류를 무시하면 화면은 비슷해도 데이터 해석이 달라진다. 같은 입력 fixture로 두 경로의 결과와 오류 정책을 확인하는 테스트가 필요하다.

성능 비교도 브라우저와 네이티브를 섞어 평균내지 않는 편이 낫다. 렌더링과 실행 환경, 디버그 도구가 다르기 때문이다. 각 플랫폼에서 어떤 조건의 지연을 줄이려는지 따로 목표를 세워야 개선 여부를 설명할 수 있다.

## 전달하는 데이터에도 비용이 있다

연산을 옮길 때는 실행 공간을 준비하고 입력과 결과를 전달하는 비용이 생긴다. 아주 작은 변환을 매번 분리하면 계산보다 준비 비용이 더 중요해질 수 있다. 코드가 더 복잡해졌는데 실제 화면 지연은 줄지 않는 상황을 피하려면 작업 크기를 비교해야 한다.

객체 전달은 자료형과 API에 따라 복사나 소유권 이전 등 동작이 다르므로 모든 데이터가 항상 같은 방식으로 복사된다고 단정하지 않았다. 다만 큰 객체 그래프를 주고받는 비용을 없는 것으로 취급할 수는 없다. 필요한 최소 입력과 결과만 남기는 설계가 유리하다.

예를 들어 원본 전체와 파싱한 객체 전체를 동시에 오래 보관하면 순간 메모리 사용량이 커질 수 있다. 화면에 필요한 식별자나 요약값만 반환해도 되는지 살펴보면 전달 비용과 화면 갱신량을 함께 줄일 수 있다. 다른 곳에서 계산한다는 것보다 결과의 크기를 줄이는 편이 먼저일 때도 있다.

짧은 isolate를 반복 생성하는 비용이 중요해지면 오래 살아 있는 작업자를 검토할 수 있다. 그 경우에는 작업 식별자, 요청 큐, 오류와 종료 메시지, 재시작까지 직접 관리할 일이 늘어난다. 단순한 단발 변환에 처음부터 영구 작업자를 만드는 것은 필요 이상의 복잡성일 수 있다.

여러 계산을 한꺼번에 시작한다고 처리량이 계속 늘지도 않는다. CPU 코어와 메모리, 전달 비용이 제한되어 있고 UI도 같은 장치 자원을 사용한다. 동시 작업 수를 정하고 최신 결과만 필요한 요청은 합치거나 이전 결과를 버리는 정책을 고려해야 한다.

바이너리 자료를 다룰 때는 전달 방식의 제약과 메모리 수명을 더 주의해서 봐야 한다. 이미지 전체를 여러 형태로 중복 생성하는지, 결과를 적용한 뒤 원본을 계속 잡고 있는지 확인한다. 측정에는 연산 시간뿐 아니라 최대 메모리와 반복 실행 뒤 남는 양도 포함하는 편이 낫다.

## 계산이 끝났을 때 화면은 달라져 있을 수 있다

사용자가 검색어를 바꾸는 동안 이전 검색 결과 계산이 늦게 끝날 수 있다. 완료된 순서대로 화면에 넣으면 새 검색 결과 위에 옛 결과가 덮인다. 연산을 다른 공간으로 옮기면서 시간 순서가 더 눈에 띄게 달라지는 경우다.

VoiceLink의 [통화 연결 코드](https://so-dak.com/webrtc-livekit-%ec%97%b0%eb%8f%99-%ed%9a%8c%ea%b3%a0-%ea%b7%b8%eb%83%a5-%ec%98%a4%ed%94%88%ec%86%8c%ec%8a%a4-%ec%84%9c%eb%b2%84-%eb%9d%84%ec%9a%b0%eb%a9%b4-%eb%90%98%eb%8a%94-%ea%b1%b0-%ec%95%84/)는 시도 번호를 비교해 오래된 비동기 결과를 구분하는 방식을 사용한다. 이는 isolate를 적용한 코드가 아니라 같은 종류의 상태 문제를 생각할 수 있는 실제 사례다. 연산 결과에도 시작할 때의 요청 식별자를 붙여 현재 요청인지 확인하는 정책을 적용할 수 있다.

화면이 아직 살아 있는지 확인하는 것과 최신 요청인지 확인하는 것은 다르다. 위젯은 존재해도 사용자가 이미 다른 입력을 선택했을 수 있다. 두 조건을 나눠야 취소된 작업이 정상 화면에 잘못 반영되는 것을 막을 수 있다.

Future의 제한 시간이 끝났다고 계산이 중단되었다고 가정해서도 안 된다. 기다리기를 중단한 뒤에도 결과가 돌아올 수 있고, 이를 채택하지 않는 처리와 실제 작업 중단은 별개다. 오래 실행하는 작업자라면 취소 메시지를 어떤 경계에서 확인할지도 설계해야 한다.

오류도 같은 요청 식별자와 연결해야 한다. 이전 요청이 실패했다고 최신 성공 화면에 오류를 띄우면 사용자는 현재 동작이 실패했다고 이해한다. 결과와 오류, 로딩 종료 모두 같은 소유권 조건으로 처리하는 편이 일관적이다.

작업 결과를 받았다고 한 번에 모든 위젯을 갱신하면 다른 병목이 남을 수 있다. 큰 목록을 다시 구성하거나 한꺼번에 알림을 보내는 비용은 주 isolate에서 발생한다. 계산을 옮긴 뒤에도 결과 적용 구간을 측정해야 처음의 끊김이 다른 위치로 이동했는지 알 수 있다.

## 비교 실험은 입력과 화면 동작을 고정한다

먼저 실제로 느린 사용자 동작을 하나 고른다. 큰 응답을 읽은 직후 목록을 스크롤하는지, 입력할 때마다 정렬하는지처럼 재현 가능한 동작이어야 한다. 단순 파싱 시간만 줄어도 사용자가 보는 지연이 달라지지 않을 수 있다.

입력은 작은 것과 큰 것, 형식이 잘못된 것을 나눠 준비한다. 데이터 크기뿐 아니라 항목 수와 중첩 깊이, 변환 후 객체 수를 기록하면 왜 시간이 달라지는지 비교하기 쉽다. 실제 사용자 자료 대신 공개 가능한 생성 데이터를 사용한다.

디버그 모드의 실행 시간만으로 성능을 판단하지 않는다. 실제 기기의 profile 모드 등 목적에 맞는 환경에서 프레임과 CPU 구간을 관찰하고, 기기와 운영체제, 앱 버전을 남긴다. 브라우저는 별도의 측정 도구와 빌드 조건을 기록한다.

연산 전후에는 전체 응답 시간, 주 isolate가 오래 점유된 구간, 프레임 지연과 최대 메모리를 함께 본다. 전체 계산은 더 오래 걸려도 화면 반응이 좋아지는 선택일 수 있고, 반대로 평균 계산은 빨라도 결과 적용 순간에 끊길 수 있다. 어떤 값을 개선하려는지 먼저 정해야 한다.

첫 실행과 반복 실행을 구분하고 여러 번 수행한 결과를 비교한다. 캐시와 초기화 비용, 장치의 발열과 다른 앱의 부하가 영향을 줄 수 있기 때문이다. 한 번 나온 좋은 숫자를 대표 결과로 고르지 않고 편차와 실패 조건을 함께 남기는 편이 낫다.

기능 정확성도 같은 실험에 포함한다. 계산을 옮기기 전후의 결과가 같고 오류 입력을 같은 방식으로 처리하는지, 취소한 요청이 화면에 반영되지 않는지 확인한다. 빠르게 틀린 데이터를 보여 주는 것은 최적화 결과가 아니다.

## 지금은 적용 결과보다 선택 기준이 남았다

현재 프로젝트에서 확인한 것은 비동기 연결과 상태 정리의 구현이며, isolate로 파싱 병목을 해결한 측정은 아니다. 따라서 프레임 저하가 사라졌다는 기존 표현을 유지하지 않았다. 실제 입력과 화면에서 병목을 찾기 전까지는 적용 여부도 열어 두는 편이 맞다.

작은 데이터라면 함수를 명확히 분리하고 호출 횟수를 줄이는 것만으로 충분할 수 있다. 서버에서 필요한 범위만 받아 오거나 이미 계산한 결과를 재사용하는 선택도 있다. isolate는 계산 위치를 바꾸는 도구이므로 불필요한 계산을 없애는 검토를 건너뛸 이유가 되지 않는다.

도입한다면 먼저 같은 변환 함수를 주 실행 경로와 분리 경로에서 비교할 수 있게 만들 생각이다. 결과 적용과 취소 정책은 공통으로 유지하고, 측정으로 효과가 확인된 플랫폼에만 적용 범위를 정한다. 효과가 없거나 메모리 부담이 커지면 되돌릴 수 있는 경계도 이때 생긴다.

이제 화면이 버벅일 때 먼저 확인할 것은 compute 호출 유무가 아니다. 계산과 렌더링 중 어디에 시간이 쓰였고, 입력을 줄일 여지가 있는지다. 옮길 작업의 크기와 결과의 수명이 설명될 때 비로소 실행 공간을 나누는 선택도 설득력을 갖는다.
