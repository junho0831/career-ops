연관관계를 LAZY로 바꾸면 당장 조회하지 않는 데이터는 줄어든다. 그런데 목록을 응답으로 바꾸는 코드가 그 연관관계를 모두 읽으면, 미뤘던 조회가 그 자리에서 한꺼번에 필요해진다. 지연시켰다는 사실만으로 쿼리가 줄었다고 말하기 어려운 이유다.

기존 글은 이 차이를 설명하다가 곧바로 fetch join을 정답으로 제시했다. 다시 정리하면서 기준을 바꿨다. 먼저 화면에 필요한 결과의 크기를 정하고, 그 결과를 어떤 쿼리로 가져올지 결정하는 편이 페이징 문제까지 설명하기에 정확했다.

검토한 VoiceLink는 Spring Boot 3.2.5를 사용하고, 공통 설정에는 배치 조회 크기 100과 Open Session in View 비활성화가 들어 있다. 아래 게시글·댓글 모델은 선택지를 비교하기 위한 설명용 모델이다. 실제 서비스에서 열한 번의 쿼리를 한 번으로 줄였다는 측정 기록은 확보하지 않았으므로 성과로 쓰지 않았다.

## 조회를 미룬 곳과 실제로 읽는 곳

게시글 열 개를 가져오는 쿼리 다음에 댓글 수를 표시한다고 가정해 보자. 매핑 과정에서 각 게시글의 댓글 컬렉션을 초기화하면 추가 조회가 생길 수 있다. 정확한 횟수는 같은 영속성 컨텍스트에 무엇이 이미 올라와 있는지와 배치 설정에 따라 달라진다.

그래서 테스트에서 쿼리 한 번만 보였다는 사실도 해석이 필요하다. 직전에 테스트 데이터를 저장하면서 연관 객체까지 메모리에 남겨 뒀다면, 실제 요청과 다른 출발점에서 조회한 셈이다. 데이터 준비와 측정을 나누고 영속성 컨텍스트를 비워야 조회 비용을 관찰하기 쉽다.

반대로 EAGER로 바꾸면 필요한 관계를 알아서 가장 효율적인 조인으로 가져올 것이라는 기대도 성립하지 않는다. 즉시 가져온다는 요구와 어떤 SQL을 만들지는 별개의 문제다. 모든 요청이 같은 관계를 필요로 하지 않으므로 매핑의 전역 설정만으로 화면별 요구를 표현하기도 어렵다.

여기서 먼저 적어 둘 것은 응답 필드다. 작성자 이름만 필요한지, 댓글 수만 필요한지, 최근 댓글 세 개까지 필요한지에 따라 데이터의 양이 달라진다. 전체 댓글을 불러와 크기를 계산하는 방식은 구현은 간단해도 필요한 정보보다 훨씬 많은 객체를 만들 수 있다.

조회 책임을 서비스 안에서 끝내려는 이유도 이 지점에 있다. VoiceLink의 설정처럼 뷰 렌더링까지 영속성 컨텍스트를 열어 두지 않으면, 응답을 만들다가 뒤늦게 지연 로딩하는 코드가 드러난다. 그 오류를 설정 하나로 숨기기보다 응답에 필요한 관계를 조회 단계에서 준비하는 편이 경계를 명확하게 만든다.

## 조인 한 번의 결과가 작다는 보장은 없다

부모 한 건과 자식 몇 건을 함께 보여주는 상세 화면이라면 컬렉션 fetch join은 이해하기 쉬운 후보다. 부모와 자식을 함께 읽으므로 이후 컬렉션 접근 때문에 개별 조회가 반복되는 경로를 줄일 수 있다. 자식이 없는 부모를 포함해야 한다면 내부 조인과 외부 조인의 차이부터 맞춰야 한다.

다음은 그 차이를 표현한 JPQL 예제다. 실제 저장소에 추가한 메서드는 아니며, 게시글 하나를 읽는 상황으로 범위를 제한했다. 접근 권한과 삭제 상태 같은 조건은 서비스 규칙에 맞춰 별도로 포함해야 한다.

```java
@Query("""
    select p from Post p
    left join fetch p.comments
    where p.id = :id
    """)
Optional<Post> findDetail(@Param("id") Long id);
```

외부 조인을 썼기 때문에 댓글이 없는 게시글도 조회 대상에 남는다. 하지만 댓글이 매우 많은 게시글이라면 SQL 결과의 행 수와 전송량은 여전히 커진다. 부모 객체가 결과에서 하나로 보이더라도 데이터베이스가 읽고 애플리케이션으로 보낸 행까지 하나였던 것은 아니다.

두 개의 컬렉션을 동시에 붙일 때는 더 조심스럽다. 댓글과 첨부 파일의 조합으로 결과가 늘어날 수 있고, 컬렉션 매핑에 따라 Hibernate가 조회 자체를 허용하지 않는 경우도 생긴다. 중복 부모를 제거하는 처리만 보고 전체 비용이 해결됐다고 판단하면 이 증가분을 놓친다.

따라서 쿼리 개수와 함께 반환 행 수, 네트워크 전송량, 객체 생성량을 봐야 한다. 한 번의 거대한 조인보다 두 번의 제한된 조회가 유리할 수 있다. 이 선택은 쿼리가 적어 보이는 코드가 아니라 실제 데이터 분포를 기준으로 비교할 일이다.

## 컬렉션을 붙인 뒤 페이지를 자르면

목록 화면에서 원하는 스무 건은 대개 부모 스무 건이다. 그런데 부모와 자식을 펼친 SQL 결과에서 스무 행을 자르면, 자식이 많은 부모 몇 개만 남을 수 있다. 데이터베이스가 제한하는 행과 화면이 세는 항목이 서로 달라지는 셈이다.

Hibernate는 컬렉션 fetch join과 페이지 제한의 조합에서 메모리 쪽 제한이 필요해지는 경우를 경고할 수 있다. 개발 데이터가 적으면 응답은 정상처럼 보이지만, 전체 결과를 읽는 비용이 데이터 증가와 함께 드러난다. 반환 개수만 검사하는 테스트로는 이 문제를 찾기 어렵다.

한 가지 대안은 먼저 정렬된 부모 식별자만 한 페이지 조회하고, 그 식별자에 해당하는 상세 데이터를 두 번째 쿼리로 가져오는 방식이다. 두 번째 조회의 IN 조건은 첫 번째 조회의 정렬 순서를 보장하지 않으므로, 응답을 조립할 때 원래 순서를 복원해야 한다.

정렬 기준에도 동률을 풀 조건이 필요하다. 작성 시각이 같은 행이 여러 개라면 식별자를 함께 정렬해야 페이지 이동이 안정적이다. 조회 사이에 새 데이터가 들어오거나 삭제되는 경우의 동작도 정해야 한다. 두 번 조회한다는 구조만으로 시점 일관성이 자동으로 생기지는 않는다.

이때 전체 건수까지 반드시 보여줘야 하는지도 살펴볼 만하다. 매번 복잡한 count 쿼리가 필요한 화면과 다음 페이지 유무만 필요한 화면은 요구가 다르다. 오프셋이 깊어지는 목록은 마지막으로 본 정렬 키를 기준으로 이어 읽는 방식까지 비교하되, 이동 가능한 페이지 형태가 달라진다는 점을 함께 판단해야 한다.

## 배치 크기 100이 뜻하는 범위

VoiceLink의 공통 설정에 있는 배치 조회 크기는 지연 로딩 대상을 모아 가져오는 데 쓰인다. 하나씩 추가 조회하는 경로를 줄이는 장치이지만, 모든 조회를 항상 한 번으로 합쳐 주는 설정은 아니다. 실제로 초기화되는 관계와 영속성 컨텍스트에 모인 대상에 영향을 받는다.

부모 목록을 페이지로 제한한 다음 필요한 컬렉션을 배치로 가져오면 부모 수를 제어하기 쉬워진다. 다만 부모 하나의 자식이 매우 많으면 배치 안의 전체 행은 여전히 커질 수 있다. 부모 개수의 상한과 자식 개수의 상한은 따로 생각해야 한다.

배치 크기를 크게 올리는 것도 무조건 좋은 선택은 아니다. 필요한 것보다 많은 대상을 함께 읽을 수 있고, 데이터베이스의 매개변수 제한이나 쿼리 계획에 영향을 줄 수 있다. 같은 설정값이라도 식별자 구조와 데이터베이스 종류가 다르면 생성되는 SQL을 다시 살펴봐야 한다.

내가 이 설정에서 확인할 지점은 두 가지다. 실제 요청에서 여러 추가 조회가 어느 정도 묶이는지, 그리고 묶은 뒤 한 번에 읽는 데이터가 감당할 크기인지다. 값이 설정 파일에 존재한다는 사실은 확인했지만, 특정 응답의 지연을 얼마나 줄였는지는 별도 측정 없이는 알 수 없다.

캐시가 켜져 있으면 이런 비교가 더 쉽게 흐려진다. 반복 실행에서 빨라진 이유가 조회 계획인지 캐시 적중인지 구분하려면 최초 요청과 반복 요청을 나눠 기록해야 한다. 애플리케이션 캐시 문제는 [갱신 경합을 정리한 글](https://so-dak.com/redis-cache-stampede-%ed%98%84%ec%83%81-%ea%b7%b9%eb%b3%b5%ea%b8%b0-%ec%ba%90%ec%8b%9c-%ec%a0%81%ec%9a%a9%ed%95%98%eb%a9%b4-db-%eb%b6%80%ed%95%98-%eb%81%9d-%ec%95%84%eb%8b%8c%ea%b0%80/)과도 연결되지만, 캐시를 붙이기 전에 한 요청이 읽는 양부터 설명할 수 있어야 한다.

## 응답에 필요한 값만 가져오는 선택

목록에 제목과 작성자, 댓글 개수만 필요하다면 엔티티 그래프 전체를 가져오지 않는 방법도 있다. 필요한 필드를 DTO로 조회하거나 댓글 수를 별도 집계로 가져오면 응답 구조와 조회 목적이 가까워진다. 읽기 전용 화면일수록 이 방식의 의도가 명확하다.

그렇다고 DTO 조회가 항상 더 빠르다는 뜻은 아니다. 조인과 그룹화가 복잡해지거나 페이지 전체의 집계 범위를 잘못 잡으면 데이터베이스 부담이 커질 수 있다. 실행 계획에서 필터가 적용되는 위치와 집계 대상 행 수를 봐야 하며, 작은 결과를 반환한다는 것과 적게 읽는다는 것도 구분해야 한다.

변경이 필요한 업무에서는 엔티티의 상태 전이와 검증 규칙이 중요할 수 있다. 조회 화면의 편의 때문에 변경 로직까지 여러 DTO 갱신 쿼리로 흩뜨리면 다른 비용이 생긴다. 목록 조회와 업무 변경이 같은 저장소 메서드를 억지로 공유할 필요는 없다.

또 하나는 누락되는 행이다. 작성자가 없는 데이터나 댓글이 없는 게시글이 조인 조건 때문에 사라지면 쿼리 수가 적어도 기능은 틀린다. 성능 비교 전에 결과 집합이 원래 요구와 같은지 검증해야 한다. 권한 필터가 빠져 더 빨라진 응답은 최적화 결과로 볼 수 없다.

정렬과 검색 조건을 문자열로 직접 이어 붙이는 예제도 피했다. 동적 조회가 필요하더라도 값은 바인딩하고, 선택 가능한 정렬 필드는 허용 목록으로 제한하는 편이 안전하다. 조회 계획을 다루는 글에서도 입력 조건의 경계가 빠지면 복사해서 쓸 때 다른 문제가 생긴다.

두 단계 조회에서 첫 번째 목록에는 있었지만 두 번째 조회 때 삭제된 부모는 어떻게 응답할지도 정해야 한다. 빠진 항목을 제외해 짧은 페이지를 반환할지, 동일한 읽기 시점을 유지할지가 서비스의 선택이다. 부족한 개수를 채우려고 무제한으로 다음 데이터를 읽으면 페이지 크기를 제한한 의미가 사라진다.

읽기 시점을 맞추려 더 강한 격리 수준을 선택하면 트랜잭션 수명과 데이터베이스 부담도 달라진다. 화면을 그리는 동안 외부 API를 기다리며 그 트랜잭션까지 유지할 필요는 없다. 조회와 응답 조립을 짧게 끝내고 외부 조회가 필요한 값은 별도 요구로 다루는 편이 원인을 추적하기 쉽다.

## 무엇을 비교해야 판단이 남는가

검증 데이터는 부모 수만 늘려서는 부족하다. 자식이 없는 부모, 보통 크기의 부모, 유난히 자식이 많은 부모를 섞어야 한 번의 조인이 만드는 차이를 볼 수 있다. 정렬 값이 같은 데이터와 페이지 경계의 삭제도 포함하면 결과 정확성까지 확인할 수 있다.

준비 단계가 끝난 뒤 영속성 컨텍스트를 비우고, 응답 변환까지 측정 범위에 넣는다. 저장소 호출 직후 시간을 멈추면 뒤에서 일어나는 지연 로딩을 놓칠 수 있다. SQL 횟수와 반환 행 수, 처리 시간, 최대 메모리를 같은 요청 단위로 기록하는 것이 비교의 출발점이다.

테스트는 특정 SQL 문자열 전체를 복사해 고정하기보다 중요한 성질을 확인하는 편이 오래 간다. 페이지의 부모 수와 순서가 맞는지, 불필요한 관계를 읽지 않는지, 데이터가 늘 때 조회가 항목마다 추가되는지처럼 실패가 의미 있는 조건을 잡는다. 버전 변경으로 SQL 형태가 달라져도 이 요구는 남는다.

개선안을 되돌릴 조건도 함께 남길 생각이다. 쿼리 횟수는 줄었는데 최대 메모리나 긴 응답의 지연이 늘었다면 기존 조회와 다시 비교한다. 평균 시간 하나를 앞세우기보다 데이터가 큰 요청에서도 결과와 자원 사용이 예상 범위에 머무는지를 우선한다.

실행 계획을 볼 때도 실제 실행을 수반하는 옵션의 비용을 기억해야 한다. 운영에서 무거운 쿼리를 그대로 다시 실행하기 전에 읽기 전용 복제본이나 검증 데이터에서 범위를 좁혀 본다. 원문 SQL과 로그에 개인 정보가 들어 있다면 공유용 기록에서는 값까지 제거한다.

이 글에서 바꾼 것은 “상세는 fetch join, 목록은 배치”라는 단정이다. 상세에도 거대한 컬렉션이 있을 수 있고 목록에도 작은 단일 연관관계만 필요할 수 있다. 다음 조회를 손볼 때는 LAZY 여부보다 먼저, 응답 하나를 만들기 위해 몇 행을 읽는지부터 적어 두려 한다.
