서버가 결과를 만들었는데 사용자는 계속 기다리는 상황을 설명하려면, 결과가 지나가는 구간부터 나눠야 한다. 데이터베이스 저장, 서버 사이 전달, 연결된 클라이언트로 전송, 화면 상태 반영은 서로 다른 완료 지점이다.

VoiceLink의 매칭 결과는 이 여러 경로를 지난다. 기존 SSE 글과 Redis Pub/Sub 글은 각 기술의 역할을 따로 나열해서 연결이 끊긴 동안 무엇으로 복구하는지 설명이 부족했다. 현재 Spring Boot와 Flutter 코드를 기준으로 전달과 복구를 같은 흐름 안에 놓았다.

이 글은 동시 사용자 수나 지연 개선을 측정한 기록이 아니다. 확인한 구현은 매칭 결과에 RabbitMQ를 우선 사용하고 Redis Pub/Sub를 대체 경로로 둔다. 클라이언트 연결은 HTTP 스트림으로 읽으며, 단순히 브라우저 EventSource의 기본 동작을 그대로 사용하는 구조로 설명하지 않았다.

## SSE는 클라이언트에 닿는 마지막 구간

서버는 매칭 연결에 SseEmitter를 만들고 매칭 상태를 이벤트로 보낸다. 기다리는 결과가 돌아오면 같은 스트림에서 다시 확인하는 흐름을 예약하고, 매칭된 결과가 나오면 전송 뒤 연결을 마무리한다. 한 연결을 영구히 유지해야만 기능이 성립하는 방식은 아니다.

Flutter는 Dio에서 스트림 응답을 받고 UTF-8 디코딩과 줄 분리를 거쳐 SSE 파서로 넘긴다. 네트워크 청크 하나가 이벤트 하나와 같다고 가정하지 않는 구조다. 한 이벤트가 여러 청크에 나뉘거나 한 청크에 여러 이벤트가 담기는 경우를 파서가 처리해야 한다.

SSE 형식에서 이벤트 이름과 데이터, 빈 줄의 의미를 구분하는 이유도 여기에 있다. 주석으로 보내는 heartbeat는 업무 결과가 아니다. 파서가 이를 JSON 데이터로 읽으려 하면 연결은 유지되는데 계속 파싱 오류가 나는 상황을 만들 수 있다.

클라이언트가 서버에 취소나 종료를 요청할 때는 별도의 API를 사용한다. SSE는 서버에서 클라이언트로 흐르는 이벤트에 적합하며, 통화 미디어 자체를 실어 보내는 경로와도 다르다. 실시간이라는 말로 모두 묶기보다 각 데이터의 방향과 수명을 나누는 편이 이해하기 쉽다.

인증도 구현 방식에 따라 달라진다. HTTP 클라이언트로 스트림을 읽는 현재 코드는 요청 인터셉터의 인증 처리와 연결된다. 브라우저의 기본 EventSource로 바꿀 때는 같은 방식으로 임의의 인증 헤더를 넣을 수 있는지부터 검토해야 한다. 토큰을 주소에 붙이는 예제로 단순히 대체하지 않았다.

## 연결을 가진 서버를 어떻게 깨울까

클라이언트의 연결 객체는 그 요청을 받은 서버 메모리에 있다. 다른 서버가 매칭 결과를 만들어도 그 객체를 직접 호출할 수는 없다. 사용자 결과를 여러 서버로 전파하고, 실제 대기 중인 연결을 가진 서버가 자신의 로컬 객체를 완료해야 한다.

현재 RabbitMQ 설정은 fanout exchange와 인스턴스용 큐를 사용한다. 각 서버가 자신의 큐로 결과를 받는 구조가 되어야 모든 서버가 담당 연결을 찾아볼 기회를 얻는다. 여러 서버가 같은 큐 이름을 공유하면 메시지를 나눠 소비하는 형태가 될 수 있어 의도와 달라진다.

확인한 큐 구성은 장기 보존용 작업 큐와 같은 보장을 전제로 하지 않는다. 익명 큐 또는 비영속·자동 삭제 성격의 인스턴스 큐를 사용한다. 서버가 사라졌다가 돌아와도 모든 과거 이벤트를 그대로 읽을 수 있다고 설명할 근거는 없다.

메시지를 받은 리스너는 공통 처리기로 넘기고, 해당 사용자의 로컬 대기가 있으면 결과를 완료한다. 대기가 없는 서버는 사용자 화면에 직접 무엇을 보낼 대상이 없다. 이 구조에서 서버 간 메시지는 사용자에게 최종 결과를 저장하는 원본이라기보다 연결된 요청을 빨리 깨우는 수단에 가깝다.

이벤트 본문에도 필요한 정보만 담아야 한다. 매칭 결과에는 입장 자격과 세션 정보가 포함될 수 있으므로 원문을 광범위하게 로그로 남기는 것은 적절하지 않다. 장애 추적에는 이벤트 종류와 처리 단계, 안전하게 제한한 식별 정보를 사용하는 편이 낫다.

## 발행 확인은 사용자 확인이 아니다

발행 코드는 RabbitMQ 확인 응답을 제한 시간 동안 기다리고, 거절이나 반환 메시지가 있으면 실패로 취급한다. 브로커에 넘기는 단계의 결과를 그냥 무시하지 않는다는 점에서 의미가 있다. 하지만 그 확인은 클라이언트 화면이 매칭 결과를 적용했다는 확인과 다르다.

발행자가 보낸 메시지의 확인과 소비자가 처리한 메시지의 확인은 각각 다른 구간을 다룬다. 소비자가 받은 뒤 SSE 전송이 실패할 수도 있고, 서버가 전송을 마친 것처럼 보여도 브라우저가 화면을 바꾸기 전에 연결이 끊길 수 있다. 완료 상태의 이름을 정할 때 이 차이를 남겨야 한다.

RabbitMQ 발행이 실패하면 Redis Pub/Sub 경로를 시도한다. 둘 다 실패하면 호출부에 실패를 전달하는 코드가 있다. 대체 경로가 있다는 사실을 전체 전달 보장으로 바꾸지 않으려면, 각 경로가 무엇을 저장하고 언제 놓칠 수 있는지 살펴야 한다.

Redis Pub/Sub는 연결되어 있던 구독자에게 실시간으로 메시지를 전달하지만, 연결을 놓친 구독자가 나중에 읽을 이력을 자동 보관하지 않는다. 복구가 필요하면 별도 저장소나 스트림 구조가 있어야 한다. 현재 서비스가 결과 캐시와 업무 상태를 따로 갖는 이유를 여기서 이해할 수 있다.

발행 확인 응답이 유실된 경우에는 원래 메시지가 전달되었는데도 대체 경로가 동작할 수 있다. 두 경로에서 같은 결과가 도착하는 가능성을 생각해야 한다. 대체 경로는 유실 가능성을 줄이는 선택이지만 중복까지 없애 주지는 않는다.

따라서 이벤트를 받았다는 이유로 통화 세션을 새로 만드는 방식은 피해야 한다. 이미 정해진 세션 결과를 반영하고, 같은 결과를 여러 번 받아도 새 통화로 중복 전환하지 않는 규칙이 필요하다. 전달 횟수와 업무 수행 횟수를 분리하는 관점이다.

## 빠른 알림이 놓친 결과를 다시 찾기

매칭 확정은 사용자별 Outbox 기록을 남기고, 발행 작업은 Redis 결과 캐시에 값을 저장한 다음 실시간 전파를 시도한다. 클라이언트가 다시 요청하면 이 저장된 결과를 찾아 사용할 수 있는 경로가 있다. 연결 하나의 생존에만 결과를 맡기지 않으려는 구조다.

Outbox가 필요한 이유는 데이터베이스에서 매칭이 확정된 사실과 외부 메시지 발행을 한 트랜잭션으로 묶을 수 없기 때문이다. 저장된 작업을 다시 선점하고 실패를 재시도하는 과정은 별도 글에서 자세히 다뤘다. 여기서는 그 작업의 성공을 사용자 확인과 같게 보지 않는 경계가 중요하다.

결과 캐시에도 유효 시간이 있다. 사용자가 오래 뒤에 돌아왔을 때 과거 결과가 없을 수 있으므로, 캐시만 최종 상태로 삼을 수 없다. 활성 통화 조회와 종료 여부 검증을 통해 지금도 사용할 수 있는 세션인지 확인해야 한다.

확인한 Redis 결과 소비는 읽기와 삭제가 별도 호출인 부분이 있다. 메서드 이름에 claim이 들어가더라도 모든 호출이 원자적 소비를 보장하는 것은 아니다. 여러 요청이 함께 결과를 읽는 경우와 읽은 뒤 응답 전에 실패하는 경우를 실제 저장소에서 검증할 필요가 있다.

실시간 처리기가 로컬 대기를 완료하면 결과 캐시를 제거하는 경로도 있다. 그 완료는 서버 메모리의 요청을 처리했다는 뜻이므로 클라이언트가 실제 받았다는 증거로 넓히지 않았다. 이후 활성 세션을 다시 조회하는 복구가 왜 필요한지 설명하는 지점이다.

복구 응답은 오래된 매칭을 무조건 되살려서는 안 된다. 사용자가 취소했거나 상대가 이미 종료한 상태라면 캐시의 예전 값보다 현재 업무 상태가 우선해야 한다. 빠른 저장소에서 찾았다는 이유만으로 지금도 유효하다고 판단하지 않는 것이 핵심이다.

## 오래된 종료 콜백이 새 연결을 지우는 문제

사용자가 매칭 화면을 나갔다가 바로 다시 들어오면 이전 연결의 종료 콜백이 늦게 실행될 수 있다. 사용자 식별자만으로 대기 상태를 지우면 새로 등록한 대기까지 제거할 수 있다. 연결의 소유권을 확인해야 하는 이유다.

로컬 대기 제거와 통화 이벤트 레지스트리는 현재 저장된 객체와 종료 중인 객체가 같은 경우에만 제거하는 경로를 둔다. 새 연결이 기존 연결을 교체해도 옛 콜백이 새 값을 지우지 않도록 하는 조건이다. 맵이 동시성 자료구조라는 사실보다 이 비교 조건이 업무 의미를 지킨다.

통화 이벤트 레지스트리는 사용자별로 하나의 emitter를 유지한다. 새 연결이 등록되면 이전 연결을 완료하는 코드가 있으므로 여러 탭에서 동시에 같은 사용자의 이벤트를 받을 수 있다고 가정해서는 안 된다. 원하는 접속 정책과 자료구조가 일치하는지 확인할 부분이다.

클라이언트 구독 컨트롤러도 현재 취소 토큰과 이벤트의 출처를 비교하고, 화면이 정리된 뒤에는 재연결 타이머가 새 요청을 시작하지 않도록 한다. 서버만 소유권을 확인해도 충분한 것이 아니라 양쪽에서 늦은 작업을 구분해야 한다.

다만 매칭 결과 전파와 통화 종료·연장 전파는 같은 구현이라고 볼 수 없다. 읽어 본 통화 이벤트 서비스는 로컬 emitter에 보내는 경로를 갖고 있다. 매칭 결과에 RabbitMQ가 있다고 종료·연장도 자동으로 모든 인스턴스에 전달된다고 설명하지 않았다.

통화 이벤트를 다른 서버에서 발생시킬 수 있다면 해당 연결을 가진 서버까지 전달하는 별도 검증이 필요하다. 재접속 때 종료 상태를 다시 알려 주는 경로는 있지만, 연결이 유지된 동안 즉시 전파되는지는 다른 질문이다. 다중 서버 테스트에서 이벤트 종류별로 나눠 확인해야 한다.

## heartbeat와 프록시를 함께 보기

업무 이벤트가 드물어도 연결 상태를 확인하려고 주석 heartbeat를 보낸다. 통화 이벤트 서비스에는 20초 주기의 처리가 있고, 매칭 스트림에는 별도 주기 계산이 있다. 클라이언트와 [프록시](https://so-dak.com/flutter-web%ea%b3%bc-spring-boot-%ec%97%b0%eb%8f%99%ec%9d%84-%ec%9c%84%ed%95%9c-nginx-%eb%a6%ac%eb%b2%84%ec%8a%a4-%ed%94%84%eb%a1%9d%ec%8b%9c-%eb%b0%8f-spa-%eb%9d%bc%ec%9a%b0%ed%8c%85-%ec%b5%9c/)의 유휴 제한 시간이 이 간격보다 짧으면 멀쩡한 연결을 반복 종료할 수 있다.

프로젝트 Nginx 문서에는 SSE 경로의 버퍼링을 끄고 읽기 제한 시간을 별도로 두는 설정이 있다. 서버가 한 줄씩 전송해도 중간 프록시가 모아 전달하면 화면에서는 결과가 한참 뒤 한꺼번에 도착할 수 있다. 애플리케이션 로그만으로 지연 위치를 확정하기 어려운 이유다.

읽기 제한 시간은 연결 전체의 최대 수명과 같은 의미로 사용되지 않을 수 있다. 실제 프록시 문서의 의미와 앞단 로드밸런서의 제한을 함께 확인해야 한다. 프록시 한 곳을 길게 설정했다고 모든 중간 장비의 유휴 정책이 바뀌는 것은 아니다.

heartbeat도 느린 클라이언트에게 쓰다 막힐 수 있다. 별도 작업자를 쓴다고 전송이 무제한으로 안전해지는 것은 아니며, 대기 작업과 쓰기 지연을 관찰해야 한다. 현재 코드는 heartbeat 작업의 완료를 기다리는 구간이 있어 작업자 수만 보고 처리량을 단정하지 않았다.

재연결에는 지연을 두되 화면을 떠난 사용자의 요청은 멈춰야 한다. 여러 사용자가 동시에 연결을 잃으면 같은 간격의 재시도가 몰릴 수 있으므로 필요하면 지연에 작은 무작위 차이를 주는 방안도 검토할 수 있다. 이는 현재 구현된 보장과 구분한 개선 제안이다.

## 끊긴 지점을 하나씩 바꾸는 검증

검증에서는 서버 두 개에 각각 대기 연결을 붙여 결과를 만들고, 연결을 가진 서버가 받는지부터 본다. 같은 큐 이름을 실수로 공유한 경우와 올바른 인스턴스 큐 구성의 차이도 확인한다. 한 서버 안에서 두 사용자를 연결한 테스트만으로 분산 전달을 증명할 수는 없다.

그다음 발행 확인 유실, 구독 중단, SSE 전송 직전 연결 종료를 각각 넣는다. 최종 화면이 중복 전환하지 않는지와 재요청이 기존 세션을 복구하는지 함께 검사해야 한다. 성공 로그 수보다 사용자별 최종 상태가 기대와 같은지가 중요한 결과다.

SSE 재접속이 이벤트를 자동으로 재생해 준다고 기대해서는 안 된다. Last-Event-ID 같은 형식을 사용할 수 있어도 서버가 이력을 저장하고 해당 위치부터 보내는 구현이 필요하다. 현재 경로에서는 업무 상태 조회를 통한 복구와 이벤트 재생을 서로 다른 기능으로 구분했다.

다음 전달 오류를 볼 때는 “메시지 발행 성공”에서 조사를 멈추지 않으려 한다. 어느 서버가 결과를 받았고 어느 연결을 완료했으며, 재접속한 클라이언트가 어떤 업무 상태를 읽었는지까지 이어서 확인할 기준이 생겼다.
