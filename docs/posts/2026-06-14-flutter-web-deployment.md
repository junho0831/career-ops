첫 화면은 열리는데 내부 주소에서 새로고침하면 실패하는 경우가 있다. 반대로 화면은 열리지만 API 응답 자리에 HTML이 들어오기도 한다. 둘 다 웹 서버의 경로 처리와 관련되지만 같은 설정 한 줄로 모두 해결할 문제는 아니다.

VoiceLink의 Flutter 웹 Dockerfile은 빌드 단계와 Nginx 배포 단계를 나눈다. 기존 글은 SPA fallback만 보여 주었지만 실제 요청은 API와 [로그인 콜백](https://so-dak.com/spring-boot-redis-jwt-access-token%ea%b3%bc-opaque-refresh-token-%ec%95%88%ec%a0%84%ed%95%98%ea%b2%8c-%ea%b4%80%eb%a6%ac%ed%95%98%ea%b8%b0/), 스트림, 정적 파일로 갈라진다. 이 경로들이 어느 서버에 도착하는지부터 다시 정리했다.

확인한 Dockerfile의 Flutter 빌드 이미지는 3.38.3이고 배포 단계는 Nginx 이미지를 사용한다. 이 글은 저장소 설정을 검토한 내용이며, 모든 외부 프록시의 실제 적용 상태를 확인한 기록은 아니다. 문서에 적힌 운영 설정과 이미지 안의 설정도 구분했다.

## 새로고침은 서버에 새 요청을 보낸다

앱 안에서 화면을 이동할 때는 클라이언트 라우터가 처리할 수 있다. 하지만 주소를 직접 열거나 새로고침하면 브라우저가 그 경로를 서버에 요청한다. 서버 파일 시스템에 같은 이름의 파일이 없으면 일반 정적 서버는 찾을 수 없다고 응답할 수 있다.

SPA fallback은 이 요청에 앱의 시작 문서를 돌려주고 클라이언트 라우터가 나머지 경로를 해석하도록 한다. 확인한 이미지 설정에는 파일과 디렉터리를 찾은 뒤 index.html로 넘기는 규칙이 있다. 이 규칙이 어느 경로에 적용되는지가 핵심이다.

API에도 같은 fallback을 적용하면 없는 API가 성공 상태의 HTML로 응답할 수 있다. 클라이언트는 JSON을 기대하다 파싱 오류를 내고, 실제 원인이 잘못된 경로라는 사실이 가려진다. 화면 경로와 서버 API 경로를 먼저 나눠야 하는 이유다.

정적 자산도 무조건 fallback하는 것이 좋은지는 검토해야 한다. 존재하지 않는 JavaScript나 이미지 요청에 시작 문서가 반환되면 상태 코드만 보는 감시는 정상으로 오해할 수 있다. 배포 검증에서는 내용 유형과 실제 파일 내용까지 확인해야 한다.

앱이 루트가 아닌 하위 경로에 배포되면 시작 문서와 자산 경로, 라우터의 기준 경로가 함께 맞아야 한다. 메인 페이지 하나를 열어 본 결과만으로 내부 화면의 직접 진입을 보장할 수는 없다. 실제로 사용하는 콜백과 설정 화면 주소를 각각 새로 열어 확인해야 한다.

## API 경로는 어디까지 유지할까

Dockerfile은 API 접두사에 해당하는 요청을 백엔드로 전달한다. 앞단 경로를 제거할지 유지할지는 백엔드 컨트롤러가 기대하는 주소와 맞춰야 한다. 프록시 설정의 슬래시 차이는 읽기에는 작아 보여도 전달되는 URI를 바꿀 수 있다.

Nginx의 proxy_pass는 URI 부분을 포함하는지와 변수 사용 여부에 따라 해석할 조건이 달라진다. 인터넷에서 찾은 한 줄을 복사한 뒤 접두사를 두 번 붙이거나 없애는 실수가 생기기 쉽다. 여기서는 실제 Dockerfile이 사용한 형태와 서버의 API 매핑을 함께 대조했다.

설정을 설명할 때는 사용자 요청 경로와 백엔드가 받는 경로를 한 쌍으로 적는 편이 좋다. 정상 API와 존재하지 않는 API를 각각 보내 보면 fallback이 잘못 개입하는지도 확인할 수 있다. 인증 실패 응답이 JSON인지 시작 문서인지도 유용한 구분이다.

프런트와 API를 같은 외부 출처 아래 제공하면 브라우저의 출처 간 요청 설정을 단순하게 만들 수 있다. 다만 이것이 인증이나 권한 검증을 대신하지는 않는다. API가 같은 도메인에 있다는 이유로 입력과 세션 검증을 생략할 수는 없다.

백엔드 컨테이너 주소는 내부 프록시가 사용하고, 브라우저에는 사용자가 접근 가능한 주소를 제공해야 한다. 컨테이너 내부 이름을 프런트 설정에 넣으면 서버 안에서는 통신되어도 사용자의 브라우저에서는 찾을 수 없다. 네트워크를 검사할 때 누가 그 주소를 해석하는지 먼저 묻는 편이 정확하다.

## 설정을 바꾸는 시점이 빌드 전이었다

Flutter 환경 코드에는 컴파일 시점의 문자열 설정을 읽는 API 주소가 있다. Dockerfile도 빌드 인자를 dart-define으로 전달해 웹 산출물을 만든다. 따라서 최종 Nginx 컨테이너에 환경 변수만 새로 넣는다고 이미 만들어진 JavaScript 안의 주소가 바뀌는 구조는 아니다.

소스의 기본 API 주소와 Docker 빌드에서 넣는 기본값도 다르다. 이미지 빌드는 상대 API 경로를 사용하지만, 별도의 로컬 빌드가 같은 인자를 주지 않으면 다른 기본값을 사용할 수 있다. 코드와 배포 설정을 따로 읽으면 이 차이를 놓치기 쉽다.

이런 설정은 빌드 산출물의 일부로 기록하는 편이 낫다. 어느 커밋을 어떤 공개 설정으로 빌드했는지 알 수 있어야 잘못된 환경으로 향하는 요청을 추적할 수 있다. 비밀값은 이 기록에도, 클라이언트 산출물에도 넣지 않는다.

클라이언트에 포함되는 설정은 사용자가 내려받아 볼 수 있다고 생각해야 한다. 서버 서명 키나 메일 자격 증명을 dart-define으로 숨긴다고 안전해지지 않는다. 공개 API 기준 경로와 서버만 알아야 할 비밀값을 같은 환경 설정이라는 이름으로 묶지 않는 편이 낫다.

한 이미지를 여러 환경에서 재사용하고 싶다면 실행 시 공개 설정 파일을 읽는 방식도 검토할 수 있다. 그 경우 시작 순서와 설정 파일 캐시, 오류 시 화면을 어떻게 처리할지가 새 요구가 된다. 지금 이미지가 그 방식을 쓰는 것처럼 설명하지 않고 도입 선택지로만 구분했다.

## 로그인은 외부 주소를 알고 돌아와야 한다

TLS를 앞단 프록시에서 끝내고 내부 HTTP로 전달하면 백엔드가 관찰하는 연결과 사용자가 본 주소가 달라진다. 로그인 제공자에 보낼 콜백 주소를 만들 때 이 차이가 중요하다. 잘못된 scheme이나 host가 들어가면 로그인 후 엉뚱한 주소로 복귀할 수 있다.

Dockerfile의 Nginx 구성은 전달받은 외부 프로토콜과 호스트 정보를 백엔드에 넘기는 경로를 둔다. 이때 헤더가 존재한다는 사실만으로 신뢰할 수 있는 것은 아니다. 신뢰한 프록시에서 들어온 값인지, 외부 사용자가 임의로 넣은 값을 그대로 사용하는지 전체 경로를 검토해야 한다.

프록시가 여러 겹이면 어느 계층이 값을 처음 만들고 어느 계층이 보존하거나 덮는지 정해야 한다. 서로 다른 규칙을 적용하면 외부 HTTPS 요청이 내부 HTTP 주소로 바뀌거나 포트가 잘못 포함될 수 있다. 최종 리디렉션 주소를 실제 브라우저에서 확인하는 검증이 필요한 이유다.

로그인 콜백 경로도 SPA 라우터가 직접 열 수 있어야 한다. 앱 안에서 이동하면 정상인데 외부 제공자에서 돌아올 때만 실패한다면 서버의 직접 진입 규칙을 의심할 수 있다. 로그인 기능 자체와 프록시 경로 문제를 나눠 확인하면 범위를 좁히기 쉽다.

현재 인증 흐름은 콜백의 일회용 코드를 API에서 교환하는 단계를 갖고 있다. 콜백 문서가 열리는 것과 코드 교환이 완료되는 것은 각각 다른 확인이다. 주소가 맞아도 잘못된 API 빌드 설정 때문에 교환 요청이 다른 서버로 향할 수 있어 두 단계를 함께 봐야 한다.

주소와 헤더를 기록할 때도 토큰과 교환 코드를 그대로 수집하지 않아야 한다. 디버깅용 네트워크 캡처를 공유하기 전에는 인증 정보와 사용자 정보를 제거한다. 문제 재현에 필요한 경로와 상태 코드만으로도 많은 설정 오류를 구분할 수 있다.

## 스트림은 일반 API 설정만으로 끝나지 않는다

매칭과 통화 이벤트는 응답이 계속 이어지는 SSE 경로다. 프로젝트의 별도 Nginx 운영 문서는 해당 경로에서 버퍼링을 끄고 읽기 제한 시간을 조정한다. 일반 API가 잘 된다는 사실만으로 스트림이 같은 방식으로 동작한다고 볼 수는 없다.

이미지 안의 일반 API 프록시와 외부 운영 프록시는 서로 다른 설정 파일이다. 어느 경로를 통과하는지에 따라 스트림 처리가 달라질 수 있다. 문서에 올바른 설정이 있다는 것과 현재 실행 중인 프로세스가 그 설정을 읽었다는 것도 별도로 확인할 일이다.

버퍼링이 켜져 있으면 서버가 작은 이벤트를 보내도 중간에서 모아 전달할 수 있다. 화면이 기다리다가 여러 이벤트를 한꺼번에 받는 현상을 서버 처리 지연으로 오해할 수 있다. 이벤트를 만든 시각과 브라우저에서 받은 시각을 함께 비교하는 편이 낫다.

WebSocket 업그레이드와 SSE는 같은 프록시 옵션이 아니다. 전자는 연결 업그레이드에 필요한 헤더와 프로토콜 조건이 있고, 후자는 HTTP 응답 스트림을 계속 전달하는 조건이 중요하다. 실시간 통신이라는 이유로 모든 경로에 동일한 예제를 적용하지 않았다.

LiveKit 미디어까지 Nginx의 HTTP 경로로 모두 해결되는 것도 아니다. 시그널링 프록시와 실제 미디어 네트워크는 따로 확인해야 한다. 프런트 배포가 성공했지만 통화가 실패한다면 연결 단계와 후보 경로를 구분해 살펴볼 필요가 있다.

제한 시간을 늘리는 것만으로 끊김을 없애려 하면 오래된 연결과 자원이 남을 수 있다. heartbeat 간격, 클라이언트 재연결 정책, 화면 종료 시 정리를 함께 맞춰야 한다. 프록시는 연결의 한 구간이며 업무 상태 복구까지 대신하지 않는다.

## 새 파일과 옛 파일이 섞이지 않게

웹 배포에서는 서버가 새 이미지를 실행해도 브라우저가 이전 자산을 들고 있을 수 있다. 시작 문서와 JavaScript, 설정 파일이 서로 다른 배포에서 섞이면 새 코드의 문제가 아닌데도 화면 오류가 생길 수 있다. 캐시 정책을 파일 역할별로 구분하는 이유다.

내용이 바뀔 때 이름도 바뀌는 자산은 오래 캐시하기 쉽지만, 같은 이름으로 바뀌는 시작 문서는 새 버전을 확인할 경로가 필요하다. 모든 파일에 같은 긴 캐시를 주면 배포 반영 시점을 설명하기 어렵다. 반대로 모든 캐시를 끄면 필요 이상의 다운로드가 생긴다.

확인한 Flutter 빌드는 PWA 전략을 끄는 인자를 사용한다. 이것만으로 과거 브라우저에 등록된 서비스 워커가 즉시 사라졌다고 단정할 수는 없다. 이전 배포에서 무엇을 제공했는지와 브라우저에 남은 등록 상태를 같이 확인해야 오래된 파일 문제를 구분할 수 있다.

이미지를 교체하는 동안 이미 열린 탭의 요청도 생각해야 한다. 옛 시작 문서가 나중에 요청할 자산이 새 배포에서 사라지면 긴 세션에서만 오류가 드러날 수 있다. 이전 자산을 일정 기간 함께 제공할지, 갱신을 안내할지 배포 방식에 맞춰 선택할 일이다.

되돌리기는 이전 이미지 태그를 아는 데서 시작하지만 거기서 끝나지 않는다. 프런트가 되돌아갔을 때 백엔드 API와 응답 필드가 호환되는지 확인해야 한다. 새 백엔드만 이해하는 요청을 보낸 옛 화면이 남아 있을 수 있어 양쪽 버전의 공존 시간을 고려한다.

배포 산출물은 같은 입력으로 다시 만들 수 있게 의존성 잠금 파일과 빌드 설정을 보관한다. 최신 태그에만 의존하면 나중에 같은 커밋으로 다른 이미지를 만들 수 있다. 실제 배포 식별자를 남기는 것은 성능 최적화보다 먼저 필요한 추적 장치다.

## 브라우저에서 확인할 결과를 정했다

검증은 첫 화면의 응답 코드로 끝내지 않는다. 내부 화면 직접 열기, 새로고침, 뒤로가기, 존재하지 않는 API, 빠진 자산 요청을 나눠 본다. 정상 API가 JSON을 반환하고 잘못된 API가 시작 문서로 바뀌지 않는지 확인하면 경로 분리가 드러난다.

로그인은 새 세션에서 시작해 콜백 복귀와 코드 교환까지 본다. 스트림은 이벤트가 생성된 직후 조금씩 도착하는지, 조용한 구간에서도 유지되는지, 화면을 떠나면 정리되는지 확인한다. 같은 출처의 일반 요청과 장기 연결을 별도 항목으로 검증하는 방식이다.

새 배포 뒤에는 기존 탭과 새 탭을 함께 확인한다. 캐시를 전부 비운 브라우저에서만 성공하면 실제 사용자가 겪을 전환 문제를 놓칠 수 있다. 반대로 오래된 자산 때문에 실패한 경우에는 요청한 파일과 배포 식별자를 비교해 코드 오류와 구분한다.

설정 변경은 문법 검사를 통과한 뒤 해당 프록시를 갱신하고, 실제 경로를 다시 요청해 확인해야 한다. 파일을 저장했다는 사실과 실행 설정이 바뀌었다는 사실을 구분한다. 문제가 생기면 보관한 이전 설정과 이미지로 되돌린 뒤 같은 검증을 반복할 수 있어야 한다.

다음에 새로고침 오류를 만나면 fallback을 먼저 넓히지 않을 생각이다. 그 주소가 화면인지, API인지, 자산인지부터 정하면 서버가 무엇을 돌려줘야 하는지도 명확해진다. 경로 하나를 살리다가 다른 경로의 실패를 HTML로 감추는 일을 피할 수 있다.
